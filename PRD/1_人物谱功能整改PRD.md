## 2. 整改背景与现状结论

人物谱现有的浏览、即时搜索、版本查看、角色设定与生成参数展示已经可用，且首次生成、停止、补齐和跳过等主流程均有入口；问题集中在“结果能否放心采用”和“高代价操作是否可控”。扫描确认：

1. **P1，并发保存可能覆盖新数据。** `BiblePage.tsx:101` 直接发送整份 `editing`；后端 `bible_ops.py:495-513` 已支持 `expected_version`，前端未传。长时间编辑期间，后台自动补入的新角色或其他窗口修改可能被旧页面静默覆盖。
2. **P1，人物多视角 QA 对用户不可见。** 后端执行单图及整包一致性 QA，但人物卡只显示“已定妆”，没有分数、问题、候选、采纳理由或证据；人脸、服装、发型漂移可能到视频阶段才暴露。
3. **P1，付费操作缺少统一预检。** 首次定妆和“重新生成当前造型包”没有汇总图片数、单价、最大重试与预算上限；后者会直接触发多图生成。单视角重做虽有确认，却仍在同步 HTTP 请求内等待生成和整包 QA。
4. **P1，定稿影响在保存后才精确计算。** 用户确认前不知道会失效的剧本、分镜、图片和视频数量，也无法评估已付费资产及预计重建费用。
5. **P2，批量修订缺少编辑保护。** 样本同时出现 9 个文本框，切导航、浏览器返回或关页没有脏数据保护；“清空”也不是立即恢复默认，容易误解或丢稿。
6. **共用体验仍不一致。** 导航缺少任务状态；全局运行提醒可能遮挡操作；项目名可能显示为 `《《斗破苍穹》》`；弹窗缺少焦点圈定/恢复；长列表管理、图片放大对比、状态中文化和提示词规范化仍需补齐。

结论：本次不推翻已有信息架构，保留高分的浏览与参数展示能力；优先补齐并发控制、人物 QA、付费预检、长任务恢复和定稿预检，再做日常编辑效率微调。

## 3. 目标与量化成功指标

### 3.1 产品目标

- 让“已定妆可用”成为可解释、可追溯、与 QA 结论一致的状态。
- 任何覆盖数据、触发付费或使下游资产失效的动作，都在执行前展示真实影响并取得明确确认。
- 让长耗时任务与长时间编辑可停止、可恢复、可合并，不因刷新、断网或并发更新丢失结果。
- 保留人物谱现有高效浏览、搜索、版本与设定信息结构，并提升长篇项目的管理效率。

### 3.2 成功指标

| 指标 | 发布门槛/目标 | 统计口径 |
|---|---:|---|
| 并发静默覆盖次数 | 0 | 旧版本提交不得覆盖服务端新版本；冲突必须进入刷新/合并流程 |
| 付费确认覆盖率 | 100% | 所有会生成图片并可能扣费的人物入口均先完成服务端预检与用户确认 |
| 取消后的误任务/误扣费 | 0 | 用户在确认卡取消后，不创建任务、不扣费、不替换资产 |
| 人物多视角 QA 可见率 | 100% | 有定妆包的角色均可查看包结论、维度结果、问题、证据与采用原因 |
| QA/状态一致率 | 100% | 任一硬失败时不得显示绿色“已定妆可用”，UI、证据与采用版本一致 |
| 单视角重做恢复率 | 100% | 刷新或断线后，可通过持久任务恢复进度并查看最终结果 |
| 定稿影响预检覆盖率 | 100% | 保存前返回受影响资产清单与费用口径；不可计算时允许保留/保存草稿，但必须阻止正式定稿，不提供降级绕过 |

| 核心 E2E 通过率 | 100% | 本文测试验收矩阵中的 P1 用例全部通过，无阻断缺陷 |
| 体验效果观察值 | 发布后 14 天内：付费取消率、版本冲突率、QA 人工复核率可被完整观测 | 用埋点建立基线，首版不虚设未经历史数据验证的下降百分比 |

## 4. 范围与非范围

### 4.1 本期范围

- 人物谱首次生成、停止、失败补齐、跳过与阶段进度。
- 证据、世界观/画风、角色卡、搜索筛选、分页、图片浏览与定妆版本。
- 单视角重做、整包重生、付费预检、持久任务和旧资产保护。
- 人物 QA 摘要、问题、候选、证据、自动/人工采用与回滚。
- 整份修订、版本并发控制、草稿/离开保护、定稿影响预检、默认值恢复。
- 新角色自动变更记录、关键事件线联动。
- 人物谱页面上的共用导航、查询态、运行提醒、项目名和弹窗基础交互。

### 4.2 非范围

- 不定义场景图纯环境、无水印、多视角差异等场景专属门禁。
- 不调整图片供应商、实际单价或计费结算规则；费用由服务端真实预检结果提供。
- 不在本 PRD 中承诺新算法模型、具体阈值或新接口路径；算法阈值与路由名须在技术设计中确认。
- 不重做分集规划页面；仅规定跳过定妆后的影响提示及下游返回入口契约。
- 不重构整套前期准备信息架构，不删除现有 Artifact、Hash、合同、评估和血缘能力。

## 6. 目标用户流程

### 6.1 首次生成与补齐

1. 用户进入人物谱；页面展示正确项目上下文、查询态和前期步骤状态。
2. 用户点击首次生成；系统先展示角色清单、每角色必需视角、预计图片数、预计/最大费用、预计耗时、重试口径、可停止说明及旧资产处理规则。
3. 用户确认后创建持久任务；页面显示“谱写”与“定妆”真实阶段，以及完成角色、当前角色、剩余视角、重试和已花费。
4. 用户可按当前阶段停止；系统保留已落盘资产并给出完成、QA 失败、缺失和未开始清单。
5. 失败补齐时，用户先查看并勾选缺失角色/视角，再进行费用预检和确认；已有合格视角不重复生成。
6. 若选择暂时跳过，系统先展示下游影响；分集页面须能看到缺口数量并一键返回对应人物谱筛选结果。

### 6.2 浏览、复核与采用

1. 用户通过名称、拼音/模糊词或身份、定妆、QA 状态筛选角色。
2. 在角色卡查看采用状态、QA 摘要和当前多视角序号；可放大或并排比较脸、发型、服装和体型。
3. 用户打开 QA 详情，查看包结论、视角级问题、候选、采用理由及证据。
4. 合格候选可人工采用；不合格候选不得以绿色可用状态呈现。若产品允许特批绕过非硬门禁，必须展示风险、记录理由并可一键回滚；硬门禁是否允许人工绕过由产品/算法评审确定，默认不允许。
5. 采用成功后，卡片、证据、版本和下游引用必须原子一致。

### 6.3 修订与定稿

1. 用户进入修订，系统基于当前人物谱版本创建编辑会话/草稿，并标记修改项和未保存数量。
2. 用户可角色级保存、撤销、查看前后差异或恢复默认描述；输入过程即时验证。
3. 导航、返回、刷新、关页或关闭弹窗时，系统检测脏状态并提供“留下继续编辑 / 保存草稿后离开 / 放弃修改”。
4. 定稿前先执行影响预检，展示失效分集、剧本、分镜、图片、视频、已付费资产和预计重建成本，并区分文字修改、角色外观修改、全局画风修改。
5. 用户确认保存时携带当前 `expected_version`。版本一致则提交；不一致返回冲突界面，按字段/角色展示“我的修改、服务端新值、合并结果”，禁止静默覆盖。
6. 保存成功后返回新版本、实际影响与可追踪任务；页面刷新为服务端确认版本。

### 6.4 单视角/整包重生

1. 用户选择单视角或当前造型包；先看到范围、图片数、单价、预计费用、最大重试预算和旧图保留策略。
2. 确认后立即获得持久任务标识；生成、单图 QA、整包 QA 分阶段展示。
3. 新图在整包判定前只作为候选，旧采用包继续服务下游。
4. 刷新/断网后可恢复；任务失败保留旧图和失败证据，可针对失败视角重试。
5. 整包通过或人工完成允许的采用流程后，才原子切换当前版本。

## 7. 详细功能需求

> 优先级沿用扫描报告口径；高分保留项以 P2 微调承接。所有“建议字段/对象”仅描述产品语义，具体接口名和存储结构待技术设计确认。

### 7.1 共用体验

| 需求 ID | 优先级 | 现状问题 | 整改规则 | 异常/边界 | 验收标准 |
|---|---|---|---|---|---|

## 8. 状态与交互规则

### 8.2 任务状态

- 合法主状态建议统一为：等待中、运行中、停止中、已停止、成功、部分成功、失败；实际枚举待技术设计确认。
- “谱写”“定妆生成”“单图 QA”“整包 QA”是阶段，不用一个模糊状态覆盖。
- 终态记录结束时间与最终历时；页面刷新后不继续累加。
- 任务按钮在请求提交后防重复；服务端幂等语义是最终保障。
- 取消/停止不等同退款；确认文案必须说明已经开始且不可撤回的成本。

### 8.3 弹窗、层级与离开

- 普通查看弹窗可由关闭按钮、Esc、遮罩关闭；编辑脏状态时三者均进入同一离开确认。
- QA 证据、候选、生成参数可作为人物详情内的二级面板；关闭后回原角色、原视角和原滚动位置。
- 付费确认不得用浏览器原生 `window.confirm` 作为最终体验；使用统一、可展示动态服务端预检数据的确认卡。
- 所有关键状态同时使用文字、图标和颜色，满足键盘与辅助技术访问。

## 9. 数据、API 与持久任务要求

### 9.1 数据语义

- 人物谱读模型至少应能提供当前人物谱版本、角色及定妆版本、适用集、当前采用视角、QA 汇总结论、问题/警告计数、候选计数和下游引用摘要；具体结构待技术设计确认。
- 保存必须使用报告已确认存在的 `expected_version` 语义；成功返回新版本，冲突返回可区分的冲突结果及最新服务端快照/差异所需数据。
- QA 结果需要同时保存包级、视角级、维度级结论、硬/软问题、评估版本、证据引用、自动采用原因；人工采用保存操作人、时间、理由、被替代版本及回滚关系。
- 草稿与定稿分离。草稿不能改变下游当前采用版本；草稿的本地/服务端持久化位置、保存周期及隐私策略待技术设计确认。

### 9.2 费用预检与提交

- 每个可能扣费的入口先调用“费用/范围预检能力”（具体接口名待确认），返回范围、图片数、单价口径、预计费用、最大重试、预算上限、旧资产策略、报价有效期和用于防重复的语义标识。
- 正式提交必须关联仍有效的预检结果与用户确认；服务端重新校验价格、范围、余额和版本。预检变化时返回“需重新确认”，不得静默扩大预算。
- 幂等由服务端保证；同一用户重复点击、网络重试或页面恢复不得创建重复付费任务。

### 9.3 持久任务

- 单视角重做、整包生成、首次定妆和批量补齐均纳入可持久恢复的任务体系；具体 Run/Step/Job 实现复用现有项目能力并待技术设计确认。
- 目标异步契约为：请求被服务端接受后 3 秒内返回 `accepted`（HTTP 202 或项目等价异步接受响应）及可跨刷新、断网、服务进程重启保持稳定的任务标识；不得在该请求内等待完整生成/整包 QA。
- 任务提供阶段、分项计数、尝试次数、已发生/预计成本、最新心跳/更新时间、错误分类、可否停止和结果引用。
- 新候选生成完成但整包未通过时，不替换当前采用资产；通过后采用切换与版本/证据更新须原子一致。

### 9.4 影响预检

- 定稿影响预检输入至少关联人物谱当前版本、草稿变更摘要和下游数据快照版本；输出按资产类型聚合并支持展开具体项。
- 保存请求须引用该预检版本/摘要。人物谱或下游关键数据变化导致结果过期时，必须重新计算并让用户再次确认。
- 费用只能来自可核验的服务端口径；无法准确预测时分别展示“确定项”和“可能项”，不得伪造精确值。
- 影响预检失败、超时或不可用时采用 fail-closed：允许继续编辑、保留或保存草稿，但客户端和服务端都不得完成正式定稿；恢复后必须重新预检并由用户确认，本文不定义可绕过该门禁的角色。

## 12. 实施阶段、依赖、风险与回滚

### 12.1 实施阶段

1. **阶段 A（P1 数据安全与付费防误触）**：`expected_version` 接入、冲突 UI、统一费用预检/确认、定稿影响预检契约；先以功能开关灰度。
2. **阶段 B（P1 任务与 QA 可信）**：单视角/整包持久任务、旧资产保护、人物 QA 状态/摘要/证据/候选与人工采用审计。
3. **阶段 C（P2 编辑与浏览效率）**：草稿/离开保护、恢复默认、筛选分页记忆、图片对比、证据完整列表、状态中文化、提示词规范化。
4. **阶段 D（历史数据与观测）**：对既有人物包回填/复验 QA 展示所需数据；建立指标基线、告警和真实样本回归。

### 12.2 依赖

- 后端现有 `expected_version` 能力及冲突差异数据。
- 可提供真实价格、范围、重试预算和幂等保障的服务端预检能力。
- 项目现有持久任务基础设施能承载图片生成与 QA 阶段；若不能，需先完成技术设计。
- 算法/QA 明确人物多视角的硬门禁、软警告、维度定义与评估版本。
- 下游资产血缘与影响计算能提供稳定快照或版本语义。

### 12.3 主要风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 历史人物包缺维度级 QA 数据 | 状态大量变灰，用户误以为资产损坏 | 分批离线复验；明确“未验证”而非“失败”；旧版是否暂时可用由迁移策略确认 |
| 影响预检成本高或结果快速过期 | 定稿等待变长 | 摘要优先、分页明细、缓存相同变更摘要；保存前做轻量版本校验 |
| 草稿与服务端并发合并复杂 | 用户看到重复/冲突 | 角色/字段级差异、明确冲突选择；不做未经确认的自动覆盖 |
| 持久任务双写或重复扣费 | 财务与资产不一致 | 服务端幂等、任务/账单/资产关联、不变量监控和补偿流程 |
| QA 新门禁使通过率下降 | 产出变慢 | 先影子评估，校准后灰度；保留旧采用图；只重做失败视角 |

### 12.4 回滚策略

- 前端新卡片状态、统一确认卡、冲突合并和新 QA 面板均以独立功能开关控制；关闭后恢复旧读展示，但**不得回滚并发版本校验与服务端幂等保护**。
- 新持久任务发布期间保留旧接口兼容只读/在途任务查询；新创建流量按开关切换，禁止同一操作同时走两条写链路。
- QA 新规则先影子运行，不自动切换采用版本；灰度出现异常时停止新规则采用，保留证据与旧资产。
- 草稿功能回滚前先提供导出/保留期，不能直接丢弃用户已保存草稿。
- 数据迁移需可重复执行并记录批次；回滚只撤展示/采用策略，不删除已生成候选、审计和账单记录。
