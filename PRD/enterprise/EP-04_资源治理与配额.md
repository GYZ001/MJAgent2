# EP-04 资源治理：额度池、三级配额、存储维度、公平调度与用量看板

> 优先级 P0 ｜ 依赖：EP-01（团队是配额归集单位）
> 一句话：把「五档硬编码订阅」升级成「企业采购额度池 → 按组织/团队/人分配 → 可看、可预警、可处置」。

---

## 1. 现状事实

- `app/quota_tiers.py`：五档 `TIER_TABLE` 硬编码常量（free/starter/standard/pro/max），维度 5 个：
  `projects` / `concurrency`（每模块） / `token` / `video_seconds` / `image`。
- `app/quota.py`(559 行)：30 天滚动周期、`quota_ledger` 按 `attempt_key` 幂等记账、预扣与退款（视频）、
  `QuotaExceeded` 带 `gate/tier/limit/used/remaining/reset_at/message`——**错误结构已经很好，保留**。
- `app/quota_addon.py` 加量包（不随周期重置）、`app/quota_expiry.py` 会员到期。
- `app/generation_concurrency.py`：进程级优先级门（interactive/recovery/batch），安全阀 32。
- **缺**：存储维度、组织/团队聚合、预算预警、项目级并发上限与防饿死（CLAUDE.md 明确记为已知欠账）、管理员的用量视图。

## 2. 目标与非目标

**P0**
1. **配额策略表化**：`TIER_TABLE` 从常量变成种子数据；企业形态下管理员可新建策略（不是改代码）。
2. **三级配额**：组织 → 团队 → 用户，取**最紧**者；任一级未配置则继承上级。
3. **新增存储维度** `storage_bytes`：按项目目录实测占用累计到团队/组织。
4. **公平调度**：项目级并发上限 + 队列按（团队剩余配额、等待时长）排序，消除单项目饿死其他项目。
5. **用量看板**：管理员可按组织/团队/用户/项目/模型看用量与趋势，80%/95% 预警。
6. **超限处置策略**：`block`（默认，拦截并给出路）| `queue`（降级排队）——由策略决定，**不提供「强制忽略」绕过**。

**P1**：按用途（文本/图像/视频）的独立预算、月度报表导出、成本分摊（与 EP-05 的成本画像对接）。
**非目标**：真实计费/发票、跨组织资源交易、GPU 直管。

## 3. 数据模型

```sql
quota_plans(
  id PK 'qp_*', org_id,                    -- org_id NULL = 全局内置（五档种子）
  key, name, builtin INT DEFAULT 0,
  period_days INT DEFAULT 30,
  limits_json,                             -- {"projects":3,"concurrency":3,"token":900000,
                                           --  "video_seconds":900,"image":9000000,"storage_bytes":null}
                                           -- null = 不限；缺键 = 继承上级
  created_at, updated_at, created_by)

quota_allocations(
  id PK 'qa_*', scope_type 'org|team|user', scope_id,
  plan_id, overrides_json,                 -- 单点覆盖，形状同 limits_json
  period_started_at, expires_at,
  created_at, created_by,
  UNIQUE(scope_type, scope_id))

quota_alerts(
  id PK, scope_type, scope_id, resource, threshold REAL,   -- 0.8 / 0.95
  triggered_at, period_index INT, notified INT DEFAULT 0,
  UNIQUE(scope_type, scope_id, resource, period_index, threshold))

-- ALTER TABLE quota_ledger ADD COLUMN org_id TEXT
-- ALTER TABLE quota_ledger ADD COLUMN team_id TEXT
-- ALTER TABLE quota_ledger ADD COLUMN project_id TEXT     -- 分账用；已有 attempt_key 幂等语义不动
```

**`users.tier` 保留不删**：SaaS 形态继续用它，企业形态下它映射到 `quota_plans` 的内置行。
`TIER_TABLE` 变成种子数据后，`app/quota_tiers.py` 保留为**迁移期的默认值来源**，不再是判定真源。

## 4. 判定链路（改一个函数，不改调用方）

`effective_limits(conn, user_id)` 是全仓唯一入口（已经是了），改为：

```
user 级分配 → 团队级分配（用户所属团队取最紧） → 组织级分配 → 内置 plan（tier 映射）
每个维度独立取最紧值；None(不限) 只在上级也不限时才生效
```

- 调用方**零改动**（这是本设计的关键：`assert_token_capacity` / `check_module_concurrency` / `reserve_video_seconds` 等全部只认 `TierLimits`）。
- `TierLimits` 新增 `storage_bytes` 字段（`dataclass(frozen=True)`，加字段即可）。
- `QuotaExceeded` 的 `tier` 字段语义扩展为「生效的策略名 + 生效层级」，消息里必须写清**是被哪一级挡的**：
  「本团队 30 天视频额度已用尽（team=内容中心，上限 900 秒）」，而不是笼统的「额度不足」。

## 5. 存储维度

- 采集：按项目目录实测占用，**异步定时采样**（复用 `jobs` 机制），不在请求路径里 `du`。
- 判据挂产物信号：目录实测字节数，不挂任何状态字段。
- 超限行为：**不删数据**，只拒绝新的媒体生成，并在项目页给出「清理建议清单」（最大的 N 个未被采纳的版本）——
  给出路，但清理动作由用户自己确认执行（破坏性操作要有原子性，先确认新状态成功再删旧的）。

## 6. 公平调度（还那笔已知欠账）

现状：`generation_concurrency` 只有进程级优先级门 + 按用户的模块并发上限；一个项目可以把全部槽位吃满。

设计：
- 新增**项目级并发上限**（`limits_json.project_concurrency`，默认 = 团队并发的 1/2 且 ≥1）。
- 队列排序键：`(团队剩余配额比例 降序, 已等待时长 降序)`——剩余多的先跑，等久的优先，两者共同防饿死。
- **判据挂实际在跑的行**（`workflow_runs`/`jobs` 的活跃状态），不挂内存计数器——重启不丢，与既有 `check_module_concurrency` 的做法一致。
- 连播队列（`app/orchestration`，任务并行数 × 每任务并行集数）接入同一套判定，**不再自建第二套并发常量**。

## 7. 用量看板与预警

```
GET /api/system/usage/summary?scope=org|team|user|project&id=&from=&to=
GET /api/system/usage/timeseries?resource=token|video_seconds|image|storage_bytes&bucket=day
GET /api/system/usage/top?dimension=team|user|project|model&resource=&limit=20
GET /api/system/quota/allocations           分配总览（谁配了多少、用了多少、还剩多少）
PUT /api/system/quota/allocations/{scope_type}/{scope_id}
```

- 数据源：`quota_ledger`（已有）+ `provider_calls`（已有）。**不新建统计表**；若查询慢，先加索引，
  真的扛不住再上物化表——但那需要单独一份实测证据，不在本单元预支。
- 预警：周期内跨过 80%/95% 时写 `quota_alerts` 并在管理员首页出横幅；同一周期同一阈值只提醒一次（`UNIQUE` 兜底）。
- 前端：新增「资源」页（管理员可见），**≤300 行**，图表用现有前端栈，不引入新图表库。

## 8. 企业形态下的入口收口

`deployment_profile=enterprise` 时：
- 支付相关路由（`app/payments/routes.py` 的 `/api/payments/orders*`）返回 **403**（不是隐藏按钮）。
- 「升级档位」文案（`app/quota_tiers.py::_UPGRADE_PATH`）替换为「联系组织管理员申请额度」，
  且错误响应里附上组织管理员的联系入口（**拦人给出路**）。
- 加量包购买入口关闭；管理员可直接给团队追加额度（`quota_allocations.overrides_json`）。

## 9. 架构约束

- 新包 `app/quota_policy/`：`plans.py`(L2) / `allocation.py`(L2) / `usage_query.py`(L2) / `api.py`(L5)。
  `app/quota*.py` 五个模块**保持现状不动**，只改 `effective_limits` 的取值来源（一个函数）。
- `app.quota` 现为 L2，新包同层；**不得反向依赖 app.quota**（避免与 `db ↔ quota ↔ quota_addon ↔ quota_tiers` 那团循环叠加）。
- 用量采样写入用**独立连接**（诊断类写入不等锁，写锁冻结事件循环的事故记录在案）。
- `TIER_TABLE` 是测试大量打桩的对象——改动后必须跑 `tests/test_quota_monkeypatch_guard.py`，
  新增可打桩常量要进 `patch_quota_everywhere()`。

## 11. 已知陷阱

1. **判据不要挂状态字段**：并发计数必须数「实际在跑的行」，不数内存计数器，也不数 `status` 字段（status 会被正常操作改坏）。
2. **预扣与计数必须同事务**：`check_module_concurrency` 的 docstring 已写明契约（占位先于判断，同一个 `BEGIN IMMEDIATE`），
   新的项目级上限照抄这个形状，不要另发明。
3. **退款要幂等**：视频退款已按 `attempt_key` 做了，新维度沿用同一机制，不要新写一套。
4. **不要为了让新维度过关而放宽旧维度**：任何「把上限调大让测试通过」的改动都要当作设计错误来查。
5. **存储采样是长任务**：大项目目录 `du` 可能几十秒，必须异步 + 有超时 + 结果带采样时间戳（UI 上如实显示「截至 X 时」）。
