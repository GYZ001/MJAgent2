# EP-03 用户生命周期：批量导入、邀请、密码/会话策略、离职移交

> 优先级 P0 ｜ 依赖：EP-01（导入时要指定团队与角色）
> 一句话：一次开 200 个号不用点 200 次；员工离职当天，他名下的项目不会连同账号一起失联。

---

## 1. 现状事实

- 开户只有单个：`POST /api/system/users`（`app/auth/admin_api.py:114`），管理员逐个建。
- 删除是软删：`DELETE /api/system/users/{id}` + `POST /users/{id}/restore`，`users.deleted_at`（`app/db.py:1772`）。
  **软删后名下项目怎么办，代码里没有答案**——这是真缺口，不是有意为之。
- `users.must_change_password`、`password_changed_at` 两列已有；`must_change_password` 已被强制（上一轮补的）。
- 会话：`user_sessions` 有 `revoked_at`/`expires_at`/`last_seen_at`/`ip`/`user_agent`，具备做会话策略的全部素材。
- 登录节流已有（`app/auth/api.py:42`），但**没有密码复杂度策略、没有历史口令校验、没有有效期**。

## 2. 目标与非目标

**P0**
1. **CSV 批量导入**：三段式（上传 → 预检报告 → 确认提交），逐行结果可下载，幂等（同 username 更新不新建）。
2. **邀请链接**：管理员生成一次性链接，用户自助设初始口令，首登强制改密。
3. **密码策略**：长度/字符类/禁用弱口令/有效期/历史 N 次不重复（可关，默认开）。
4. **会话策略**：空闲超时、最大会话时长、单账号并发会话数上限、管理员强制下线。
5. **停用与离职移交**：停用即所有会话失效；软删前**必须**处置名下项目（转移给指定用户或团队），不处置不许删。
6. 全部动作进审计（导入批次、逐行结果、移交对象）。

**R2**：SCIM 2.0（IdP 侧驱动的自动增删改）、AD 组同步。
**非目标**：自助注册（企业形态明确不做）、邮件系统（邀请链接由管理员自行分发，不做 SMTP 集成）。

`password_min_length`(默认 12)、`password_classes`(默认 3)、`password_max_age_days`(默认 0=不过期)、

## 4. CSV 导入契约

**列**：`username,display_name,email,employee_no,team,role,tier_or_quota_plan`（表头必需，顺序无关，多余列忽略）。
**编码**：UTF-8 / UTF-8-BOM / GBK 自适应探测（国内 Excel 默认导出 GBK，探不出就明确报错，**不猜**）。
**上限**：单批 1000 行（超出直接拒绝并说明，不做分片）。

三段式：
```
POST /api/system/users/import/preview   (multipart) → 逐行判定，返回 batch_id + 报告，**不写库**
POST /api/system/users/import/{batch_id}/apply     → 只应用预检通过的行，返回逐行结果
GET  /api/system/users/import/{batch_id}/report    → CSV 下载（含失败原因列）
```

**逐行判定必须区分四种结果**，不许合并成「成功/失败」两种：
`create`（新建）/ `update`（已存在，更新展示名/团队/角色）/ `skip`（完全一致，无变化）/ `error`（带具体原因与列名）。
理由：企业管理员反复导入同一份花名册是常态，「更新」和「跳过」被混报成「成功」会掩盖真实变更面。

**初始口令**：三选一策略（随机生成并在报告中一次性下发 / 统一初始口令 / 生成邀请链接）。
无论哪种，`must_change_password=1`。随机口令**只在 apply 的响应与报告 CSV 里出现一次**，不落明文库。

## 5. 离职移交（本单元的真缺口）

停用（`disabled`）：
- 立即 `revoked_at` 全部会话；名下正在跑的任务**不中断**（避免毁掉在途产出），但不能再发起新任务。
- 名下项目仍可被组织管理员访问（EP-01 的 `org_admin` 判据）。

删除（软删）：**前置强制处置**。
```
GET  /api/system/users/{id}/assets      → 名下项目数、在途任务数、占用存储、被引用的团队授权
POST /api/system/users/{id}/handover    → body: {to_user_id | to_team_id}，转移 projects.owner_user_id 并落 project_grants
DELETE /api/system/users/{id}           → 若仍有未处置资产 → **409** 并返回资产清单（不是静默删）
```

> 这条是「拦住用户时必须给出路」的正例：409 的响应体里直接带上 `handover` 接口所需的全部参数。

## 6. 邀请链接

- token = `secrets.token_urlsafe(32)`，**只存 SHA-256**（与 `mcp_tokens`、`user_sessions` 既有做法一致）。
- 默认 7 天过期、一次性消费（`accepted_at`）、可撤销。
- 接受页 `/invite/{token}`：设口令 → 建账号（按邀请里预置的团队/角色）→ 直接登录。
- **邀请不绕过密码策略**，且接受时校验邀请是否仍有效（组织被停用、角色被删 → 明确报错并提示联系管理员）。

## 7. 架构约束

- 新包 `app/provisioning/`：`csv_parse.py`(L1，纯解析零 db) / `importer.py`(L2) / `invitations.py`(L2) / `handover.py`(L2) / `api.py`(L5)。
- **`csv_parse.py` 必须零 db 依赖**——这样导入预检可以纯函数测试，1000 行样例走内存，不碰库。
- 移交是状态转移类写入：**必须显式声明用谁的事务**，不得在调用方连接上隐式提交（本仓库已因此三次毁掉真实数据）。
- 密码哈希继续用 `app/auth/passwords.py`，**不得新写一份**。

## 9. 已知陷阱

1. **导入的幂等键是 `username` 不是行号**：同一批里出现重复 username 必须在预检阶段就报错，而不是后写覆盖先写。
2. **报告里的明文口令是一次性资产**：apply 响应与报告 CSV 之外，任何地方（日志、审计 args_json）都不许出现——
   `app/audit/redact.py` 已有脱敏机制，新字段要登记进去，否则会静默写进审计表。
3. **移交要连带授权**：只改 `projects.owner_user_id` 不迁 `project_grants` 会让协作者集体失去访问。
4. **停用与删除的语义不能混**：停用可逆、删除需前置处置。UI 上两个按钮的文案必须与后端行为完全一致（界面不许撒谎）。
5. **1000 行导入不要一个事务写到底**：SQLite 长写事务会阻塞整站（写锁冻结事件循环的事故记录在案）。分批提交，每批 ≤50 行，
   失败可续跑，报告里记录已提交批次。
