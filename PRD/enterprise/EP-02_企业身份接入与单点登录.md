# EP-02 企业身份接入与单点登录（SSO）

> 优先级 P0 ｜ 依赖：EP-01（自动开户要落到具体团队与角色）
> 一句话：员工用公司账号登录，登录即按规则落到组织/团队/角色；本地账号退为 break-glass 与服务账号。

---

## 1. 现状事实

- `users` 表已有 `auth_provider TEXT NOT NULL DEFAULT 'local'` 与 `external_subject TEXT`（`app/db.py:81-82`）——接缝在，实现为零。
- 登录只有 `POST /api/auth/login`（用户名 + 口令，带失败节流 `_check_login_throttle`）。
- 会话机制成熟：`user_sessions` 表 + `X-Manju-Session` 头 + 滑动过期 + `revoked_at`，SSO 只需**复用**它签发会话，不需要新传输层。
- 依赖为零：无 `authlib`/`python-jose`/`cryptography`。`app/payments/crypto_rsa.py` 有手写 RSA-SHA256 PKCS#1 v1.5 **验签**（公钥模幂，无秘密输入，无时序问题），
  `crypto_asn1.py` 能从 PEM/SPKI/证书取 `(n, e)`。**没有** JWK→`(n,e)` 解析，**没有** ES256。

## 2. 目标与非目标

**P0**
1. 通用 **OIDC Authorization Code + PKCE**，覆盖 Microsoft Entra ID / Okta / Keycloak / Authing 等标准 IdP。
2. 预置三个国内 profile：**企业微信 / 飞书 / 钉钉**（OAuth2 + 各自的用户信息端点，差异收进 profile 配置，不是 if-else 分支）。
3. **JIT 自动开户**：首次登录按映射规则建账号、入组织/团队、授角色。
4. **账号绑定/解绑**：已有本地账号可绑定 IdP 身份（按 `sub`，不是 email）。
5. **强制 SSO 开关** + **break-glass**：可关闭本地口令登录，但必须保留至少一个可登录的超级管理员通道，且这条通道要在 UI 上说清楚怎么用。
6. 全链路进审计：登录成功/失败/自动开户/角色映射结果，都进 `operation_audit`。

**P1**：RP-Initiated Logout（IdP 登出联动）、IdP 侧停用同步（登录时校验 + 定期回扫）。
**R2**：SAML 2.0、LDAP/AD 直连、SCIM（在 EP-03）。
**非目标**：自建 IdP、多因素认证（交给 IdP 做，这是选 SSO 的意义）。

## 3. 数据模型

```sql
identity_providers(
  id PK 'idp_*', org_id, kind 'oidc|wecom|feishu|dingtalk',
  name, enabled INT DEFAULT 0,
  issuer, client_id, client_secret_enc,     -- 密文，复用 EP-05 的凭据加密
  discovery_url, authorize_url, token_url, userinfo_url, jwks_url,
  scopes TEXT,                               -- 空格分隔，默认 'openid profile email'
  claim_map_json,                            -- {"subject":"sub","username":"preferred_username","display_name":"name","email":"email","dept":"department"}
  provision_json,                            -- 见 §5 映射规则
  allowed_domains TEXT,                      -- 邮箱域白名单，空 = 不限
  created_at, updated_at, created_by)

user_identities(
  user_id, idp_id, external_subject,
  linked_at, last_login_at,
  PRIMARY KEY(idp_id, external_subject))    -- sub 是唯一键，不是 email

sso_auth_requests(                           -- state/nonce/PKCE 的一次性凭据，10 分钟过期
  state PK, idp_id, nonce, code_verifier, redirect_to, created_at, consumed_at, ip)
```

`users.auth_provider`/`external_subject` 两列**保留但降级为展示字段**，真源是 `user_identities`（一个人可能绑多个 IdP）。

## 4. 登录流程（必须逐项校验，不许省）

```
GET  /api/auth/sso/providers                 → 登录页可见的 IdP 列表（只回 id/name/kind，不回任何密文）
GET  /api/auth/sso/{idp_id}/start?redirect_to=/  → 302 到 IdP；落 sso_auth_requests(state,nonce,code_verifier)
GET  /api/auth/sso/{idp_id}/callback?code&state  → 换 token → 验 id_token → 解析 claims → 开户/绑定 → 签发会话 → 302 回前端
POST /api/auth/sso/link                      → 已登录用户绑定 IdP
DELETE /api/auth/sso/link/{idp_id}           → 解绑（最后一个登录方式不许解绑，422 并说明）
```

**id_token 校验清单（缺一条即视为未实现）**：
`iss` 精确匹配、`aud` 含 client_id、`exp`/`iat` 带 ≤120s 时钟偏移、`nonce` 与 `sso_auth_requests` 一致、
签名验证（RS256 必须，ES256 视依赖决策）、`sub` 非空。
**state 一次性消费**（`consumed_at` 落库，重放直接拒）。**PKCE `code_verifier` 必须**（S256）。

**企业微信/飞书/钉钉 profile 的差异**（不是 OIDC，是 OAuth2 + 私有用户信息端点）：
差异只落在 `authorize_url`/`token_url`/`userinfo_url`/`claim_map_json` 四个配置字段 + 一个「取 access_token 的参数名」适配点。
**禁止为每家写一条 if 分支**——这正是「禁止黑白名单与枚举穷举」的典型场景；新增一家 IdP 应当只需要一条配置行。

## 5. 自动开户与映射规则（从数据推导）

```json
{
  "auto_create": true,
  "default_team_id": "team_xxx",
  "default_role_id": "role_producer",
  "rules": [
    {"claim": "department", "op": "equals", "value": "内容中心", "team_id": "team_content", "role_id": "role_producer"},
    {"claim": "groups", "op": "contains", "value": "manju-admins", "role_id": "role_org_admin"}
  ],
  "on_no_match": "default"          // default | reject
}
```

- 规则按顺序匹配，命中即用；未命中走 `on_no_match`。
- **禁止把 IdP 的管理员标记自动映射成 `is_system_admin`**——超级管理员只能由既有超级管理员在本系统内授予。
  这是刻意的：IdP 被攻破时不应直接失守本系统的最高权限。
- `auto_create=false` 时，未预先开户的用户登录 → 明确提示「你的账号尚未开通，请联系管理员」+ 管理员侧生成一条待办（**拦人必须给出路**）。

## 6. 强制 SSO 与 break-glass

设置项 `local_login_policy`：`enabled`（默认）| `admin_only` | `disabled`。
- `disabled` 时仍保留一条本地通道：**超级管理员 + 一次性恢复码**（`scripts/create_admin.py` 同族的 `scripts/break_glass_login.py`，需服务器 shell 权限），
  使用后写审计并强制轮换。
- 切换到 `disabled` 前**必须**做一次「SSO 可用性自检」（真实走一遍 discovery + token 端点连通），不通过则拒绝切换。
  理由：这是唯一一个「配错了就没人能登录」的开关，不能让它靠人自觉。

## 7. 依赖决策（需用户拍板，回退方案已备）

**方案 A（推荐）**：新增 `cryptography`。RS256/ES256 验签、JWK 解析、EP-05 的 AES-GCM 加密一次性解决，且它是审计过的库。
**方案 B（否决 A 时的回退）**：复用 `app/payments/crypto_rsa.py` 的 PKCS#1 v1.5 验签，自写 `JWK(n,e) → int` 解析（约 30 行，base64url 大端整数），
**只支持 RS256**，在 IdP 配置页明确标注「不支持 ES256，请在 IdP 侧选择 RS256」。
**两个方案都禁止**：跳过签名校验、只信 `userinfo` 端点、用 `verify=False` 走 HTTPS。

## 8. 架构约束

- 新包 `app/sso/`：`store.py`(L2) / `oidc.py`(L3，出网) / `profiles.py`(L1，纯配置模板) / `provision.py`(L2) / `api.py`(L5)。
- 出网调用统一走 `httpx`（已在依赖里），超时按实测的 5–8 倍设，**不得裸 `requests`**。
- 新文件 ≤500 行；`oidc.py` 若因校验清单超长，拆 `oidc_verify.py`，**不得进 baseline**。
- 密文字段读写只经 EP-05 的加密模块，**不得在 `app/sso/` 里再写一份加解密**。

## 10. 已知陷阱

1. **email 不是身份**：企业邮箱会回收再分配。唯一键必须是 `(idp_id, sub)`。用 email 做键，一次人事变动就是一次越权。
2. **`sso_auth_requests` 会无限增长**：过期清理写进已有的 retention 机制，不要新开一个定时器。
3. **回调 URL 必须白名单**：`redirect_to` 只允许本站相对路径，否则是开放重定向。
4. **时钟偏移**：服务器与 IdP 时钟不同步是最常见的「配好了却登不上」，允许 ≤120s 并在错误信息里直接写出两边时间差。
5. **不要在同步依赖里写 ContextVar**（本仓库鉴权曾因此静默 fail-open）——SSO 的身份注入必须在中间件里做，与既有 `bind_request_principal` 同一条路径。
6. **企业微信/飞书的 access_token 有中心化频控**：拿 token 的调用要有进程内缓存与并发去重，否则一次批量登录就会被限流。
