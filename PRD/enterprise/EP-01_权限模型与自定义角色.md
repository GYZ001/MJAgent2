# EP-01 组织、团队、项目授权与自定义角色

> 优先级 P0 ｜ 依赖：无 ｜ 被依赖：EP-02 / EP-03 / EP-04
> 一句话：把已有的 76 条命令元数据变成**可编辑的角色**，把「1 账号 1 独立空间」升级成「组织内可协作、可授权、可审计」。

---

## 1. 为什么必须做（企业买家的原话形态）

- 「我们 30 个人共用一个项目，谁能改剧本、谁只能看片，得分开。」→ 今天做不到：登录即对自己名下项目全权，且项目不能共享。
- 「外包的剪辑不能碰模型配置，也不能删集。」→ 今天只能给他一个独立账号，然后**项目没法给他看**。
- 「审计要能答出『这条改动是谁批的』。」→ 审计表字段齐，但 actor 只有两种身份，答不出「以什么角色」。

## 2. 现状事实（核实过）

- `app/auth/principal.py`：`Principal(user_id, username, is_system_admin)`；`all_scopes` 恒返回全部 6 个 scope；
  `owns(owner_user_id)` 是全部隔离判据。历史上的四档团队角色（`ROLE_SCOPES`）已随工作空间模型一并退场。
- `app/authz/resolve.py`（275 行）：HTTP 边界把路径参数解析成归属项目，四种结果 owner/admin_only/creator/none，不 fail-open。
- `app/capabilities/`：76 条命令，每条自带 `scopes`/`risk`(R0–R3)/`confirmation`/`admin_only`/`rest_routes`；
  另有 74 条豁免路由（每条有书面理由）。`CommandBus._run_pipeline` 已有 `_authorize`，且位置在幂等缓存查询**之前**。
- `mcp_tokens.scopes_json` 是全仓唯一真正在做细粒度授权的地方。

**结论：权限素材已经齐了，缺的只是「主体侧」——把角色从两档常量变成数据。**

## 3. 目标与非目标

**P0（本单元交付）**
1. 组织（org）与团队（team）实体，单租户下一个默认组织，回填零风险。
2. 项目授权 `project_grants`：项目可授予团队或个人，角色化。
3. 角色成为数据：内置模板是**种子行**不是代码分支；支持自定义角色（复制模板后加减权限点）。
4. 权限点目录**从能力目录推导**，新增命令自动出现，守卫测试保证不漏。
5. `manju:generation-media` 拆成「发起」与「决策」两个子 scope（上一轮标记为 P2 的那笔账，现在必须还——否则审校角色做不了审校）。
6. 判定统一入口：`Principal.can(command, target)`，Bus 与 HTTP 边界各用各的一半，不重叠。

**P1**：角色继承与层级、按项目的临时授权（带到期）、权限点分组的 UI 编辑器体验优化。
**非目标**：多租户、审批流、ABAC（属性表达式）、把 `admin_only` 语义改写。

## 4. 数据模型（新增 6 表 + 1 列，全部 `CREATE TABLE IF NOT EXISTS` 追加）

```sql
orgs(id PK 'org_*', tenant_id TEXT NOT NULL DEFAULT 'default',
     name, status 'active|disabled', created_at, created_by)

teams(id PK 'team_*', org_id NOT NULL, name, description,
      status, created_at, created_by, UNIQUE(org_id, name))

team_members(team_id, user_id, role_id, created_at, created_by,
             PRIMARY KEY(team_id, user_id))

roles(id PK 'role_*', org_id,            -- org_id NULL = 全局内置模板
      key TEXT,                          -- 'owner'/'org_admin'/'producer'/'reviewer'/'viewer'/自定义
      name, description,
      builtin INT NOT NULL DEFAULT 0,    -- 内置模板不可删、不可改权限点
      created_at, created_by, updated_at,
      UNIQUE(org_id, key))

role_permissions(role_id, permission_key, PRIMARY KEY(role_id, permission_key))
      -- permission_key = 命令名（如 'video.generate_shot'）或路由组键（如 'route:GET /api/projects'）

project_grants(project_id, subject_type 'user|team', subject_id, role_id,
               created_at, created_by, expires_at,
               PRIMARY KEY(project_id, subject_type, subject_id))

-- ALTER TABLE users ADD COLUMN org_id TEXT      （回填 org_default）
-- ALTER TABLE projects ADD COLUMN org_id TEXT   （回填 org_default）
```

`is_system_admin` **保留不动**，语义收窄为「超级管理员 / break-glass」：不进角色表、不可被自定义角色模拟、
仍是 `admin_only` 那 10 条命令的唯一持有者。

## 5. 权限点目录：从数据推导，不写枚举

```
permission_key ::= <command_name>              # 76 条，来自 registry.commands
                 | "route:<METHOD> <path>"     # 74 条豁免路由，来自 registry.rest_exemptions
                 | "read:project"              # GET 读面统一一条（沿用现有「GET 缺省要 manju:read + 成员资格」的约定）
```

- 目录构建函数 `build_permission_catalog()` 遍历运行时 registry，**不得维护第二张名单**。
- 每个权限点带展示元数据：`title`/`risk`/`scopes`/`side_effect`（全部来自 `CommandSpec`，直接透出）。
- **守卫测试**：`len(catalog) == len(registry.commands) + len(registry.rest_exemptions) + 1`，
  新增命令若没有归到任何内置模板，测试报出「新命令未归类」并列名（不是失败即拦，而是强制有人裁决）。

**为什么不复用 6 个 scope 做角色**：实测这 6 个 scope 是**按资源种类切的，不是按角色切的**。
上一轮已经踩过：只给审校 `read+delivery`，他将无法确认分镜（`storyboard.confirm` 要 `generation-media`）、
无法采纳视频版本（`video.adopt_version` 要 `project-write`）。scope 留给 MCP 服务账号继续用，角色走权限点。

## 6. 内置角色模板（种子数据，可复制成自定义角色）

| 模板 key | 名称 | 权限点范围 | 说明 |
|---|---|---|---|
| `org_admin` | 组织管理员 | 本组织全部命令 − `admin_only`；+ 成员/团队/配额分配 | 不能改模型配置与系统设置 |
| `producer` | 制作 | 全部 R0–R2 生产命令 + `media:generate` | 不能交付审批、不能删集 |
| `reviewer` | 审校 | 只读 + `media:decide` 子集（`storyboard.confirm`/`video.adopt_version`/`reference.review`/`video.stop_*`）+ 交付 5 条 | **不能发起付费生成** |
| `viewer` | 只读 | `read:project` | |
| `owner` | 项目所有者 | 本项目全部命令 − `admin_only` | 兼容今天的行为，迁移后每个用户对自己名下项目自动持有 |

**审校角色是本单元的正确性试金石**：验收必须断言 `video.generate_shot` 被拒、`video.adopt_version` 放行。

## 7. scope 细分（必须做，且必须保持并集不变）

```
manju:generation-media  →  manju:media-generate  ∪  manju:media-decide
```
- `CommandSpec.scopes` 逐条重标：发起类（`video.generate_*`、`portrait.generate`…）→ `media-generate`；
  决策类（`storyboard.confirm`、`video.adopt_version`、`reference.review`、`video.stop_*`）→ `media-decide`。
- **兼容**：MCP token 持有旧的 `manju:generation-media` 时，判定层展开为两个新 scope 的并集——
  旧 token 权限**一点不变**，这是硬要求（`app/mcp/auth.py` 的既有 token 不能因为一次重构而失效或膨胀）。
- 守卫测试：`ALL_SCOPES` 的旧集合与新集合按并集关系逐条对齐；任一命令的 scope 集合为空则测试红。

## 8. 判定链路（不改既有分工）

```
HTTP 边界（app/authz/resolve.py 扩展）      →  这条数据属不属于你
   owner → 换成 accessible(project_id, principal)：
           owner_user_id 命中  OR  project_grants 命中（个人/所属团队） OR  org_admin 同组织 OR 超级管理员
   admin_only / creator / none 三种结果的语义**不变**

CommandBus._authorize（位置不动）           →  这个动作你能不能做
   principal.can(spec.name, target) ：查 role_permissions
   spec.admin_only and not is_system_admin  → 拒绝（语义不变）
```

**三条硬约束**（都是踩过的坑）：
1. `_authorize` 的位置**必须**保持在幂等缓存查询之前。
2. **空集合不等于放行**：用户无任何角色 → 拒绝一切写操作，不得因 `role_permissions` 为空而短路跳过检查。
3. 跨组织访问一律返回 **404**（与既有约定一致，不用 403 泄露 id 存在性）；403 只用于「看得见但角色不够」。

## 9. API 契约（新增，全部走 Bus 或显式登记豁免）

```
GET    /api/orgs/current                     组织信息 + 我的角色
GET    /api/teams                            我可见的团队；管理员见全部
POST   /api/teams                            建团队            [org_admin]
PUT    /api/teams/{team_id}                  改名/停用         [org_admin]
POST   /api/teams/{team_id}/members          加人（批量，body: [{user_id, role_id}]）
DELETE /api/teams/{team_id}/members/{user_id}
GET    /api/roles                            角色列表（内置 + 自定义）+ 权限点目录
POST   /api/roles                            自定义角色（可 from_template）
PUT    /api/roles/{role_id}                  改权限点（内置模板拒绝，422）
DELETE /api/roles/{role_id}                  引用检查：被 team_members/project_grants 引用则 409 并列出引用方
GET    /api/permissions                      权限点目录（含 title/risk/side_effect）
GET    /api/projects/{project_id}/grants     项目授权列表
POST   /api/projects/{project_id}/grants     授予（user|team + role）
DELETE /api/projects/{project_id}/grants/{subject_type}/{subject_id}
```

前端：`AccountAdminPage.tsx`（294 行）扩成「成员 / 团队 / 角色」三个标签页；
项目侧在项目设置里加「协作者」区块。**新前端文件 ≤300 行**，超了就拆组件。

## 10. 迁移与兼容（零行为变化是硬指标）

1. `init_db()` 引导：无 org 时建 `org_default`；所有 `users.org_id`/`projects.org_id` 回填之。
2. 种子 5 个内置角色模板。
3. 每个既有用户对自己名下项目自动等价于 `owner` 模板——**不写 grant 行**，由 `owner_user_id` 判据继续兜底（保持最短路径）。
4. **回归矩阵证明零变化**：迁移前后，对同一组请求（每类角色 × 代表性端点）的响应码逐条对比，必须完全一致。

## 11. 架构约束（落地时逐条对照）

- 新包：`app/orgs/`（store/service/api）、`app/authz/` 扩展（policy 纯判定 / resolve 已有）。
- 层号建议（落地前用 `py scripts/arch_graph.py --check-layers` 复核）：

## 13. 已知陷阱

1. **别在数据访问层加 `AND org_id=?`**：全仓 361 处直接 `WHERE id=?`，漏一处就是越权。隔离继续在 HTTP 边界一次性完成。
2. **`admin_only` 不能当角色标记用**：它现在的职责是把 10 条命令挡在非人类调用方（MCP/Agent）之外，改语义会让它们漏出去。
3. **角色删除必须做引用检查**，否则会出现「用户挂着一个不存在的角色」→ 判定分支落到未定义状态。fail closed。
4. **团队成员角色与项目授权角色会冲突**：同一用户可能通过两条路径拿到不同角色。取**并集**（权限更宽者胜）并在 UI 显式展示来源，
   不要做「就近覆盖」——那种规则用户永远算不明白，出事故时也复盘不出来。
5. **前端隐藏只是体验，后端才是边界**：菜单收口与 API 拒绝必须同时做，且验收以 API 为准。
