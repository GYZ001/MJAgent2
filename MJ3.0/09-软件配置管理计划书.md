# MJAgent 3.0 软件配置管理计划书

- 文档编号：MJ3-SCMP-001
- 版本：0.1.0
- 状态：立项评审稿
- 关联文档：MJ3-SRS-001、MJ3-ARCH-001、MJ3-TEST-001

## 1. 目的

本计划建立 MJAgent3.0 从需求到生产运行的统一配置管理制度，使任意构建、运行和交付件都能回答：使用了什么代码、数据库、领域合同、Prompt、模型、参数、质量策略、基础设施和批准记录；发生问题时能否准确复现、影响分析和安全回滚。

## 2. 管理目标

1. 每个配置项有唯一标识、所有者、版本、状态和变更记录；
2. 代码、数据结构、AI 行为和运行策略共同版本化，不把 Prompt/模型当成站外口头配置；
3. 开发、测试、预发和生产之间的差异显式声明；
4. 发布构建可复现、可验证、可审计，二进制与源码可对应；
5. 数据库和 Artifact 合同采用向前/向后兼容迁移，历史证书可持续验证；
6. 紧急变更也经过最小审批、自动检查、审计和事后复盘。

## 3. 适用配置项

### 3.1 配置项清单

| 类别 | 配置项 | 标识/版本方式 | 主要所有者 |
|---|---|---|---|
| 产品 | 需求、用例、验收标准 | 文档编号 + 版本 | 产品负责人 |
| 架构 | 架构文档、ADR、威胁模型 | `ADR-NNN` + 状态 | 架构/安全负责人 |
| 源码 | 前端、API、Worker、领域库、工具 | Git commit SHA | 研发负责人 |
| API | OpenAPI、事件 Schema、错误目录 | major/minor + hash | API 负责人 |
| 数据 | SQL Schema、迁移、种子数据、保留策略 | migration ID | 数据负责人 |
| Artifact | S2B/B2V、Ledger、Manifest、Certificate Schema | contract name + semver | 领域负责人 |
| AI | Prompt、模板、输出 Schema、模型分配 | immutable version | 模型质量负责人 |
| 质量 | Evaluator、Gate、阈值、Golden Set | policy/dataset version | 质量负责人 |
| 供应商 | Adapter 合同、能力、参数映射 | adapter version | 集成负责人 |
| 运行配置 | Platform/Tenant/Project/Run 策略 | ConfigVersion/Snapshot | 运维/租户管理员 |
| 基础设施 | IaC、镜像、Helm/Compose、网络策略 | Git SHA + image digest | 运维负责人 |
| 依赖 | 锁文件、容器基础镜像、系统包 | lock hash/SBOM | 研发/安全负责人 |
| 测试 | 用例、Fixture、Golden Set、报告 | suite/data/build version | 测试负责人 |
| 发布 | Release Manifest、迁移计划、签名、回滚包 | release version | 发布负责人 |

数据库中的密钥仅保存 `secret_ref`，密钥值由 KMS/Secrets Manager 或私有密钥库管理，其轮换版本进入审计但不得写入 Git、日志或文档。

### 3.2 基线类型

| 基线 | 建立时点 | 内容 | 变更权限 |
|---|---|---|---|
| 需求基线 | M0 评审通过 | PRD、SRS、用例、验收 | 变更委员会 |
| 架构基线 | M0/M1 设计评审 | 架构、ADR、合同、数据模型 | 架构评审组 |
| 开发基线 | 每次主干绿色 | 源码、迁移、锁文件、自动测试 | 合并审批者 |
| 测试基线 | 候选版创建 | 构建、配置、数据集、用例 | 测试/发布负责人 |
| 发布基线 | Go 决策 | 签名镜像、Manifest、迁移、策略 | 发布负责人 |
| 运行基线 | 部署完成 | effective 配置、流量、凭证引用、观测 | 运维负责人 |

## 5. 版本与标识规则

### 5.1 产品版本

采用语义版本 `MAJOR.MINOR.PATCH`：

- MAJOR：公开 API 或业务合同不兼容；
- MINOR：向后兼容的新能力；
- PATCH：向后兼容的修复和内部优化；
- 候选版：`3.0.0-rc.1`；
- 构建元数据由 Release Manifest 记录 Git SHA、流水线和构建时间，不依赖可变标签。

### 5.2 独立版本对象

| 对象 | 规则 |
|---|---|
| HTTP API | URL 保留 major，如 `/api/v3`；向后兼容字段用 minor 文档化 |
| 事件 | `event_type` + `schema_version`；消费者声明可读区间 |
| 数据库迁移 | 单调唯一 ID；已进入共享环境后不可改写原文件 |
| Artifact 合同 | 独立 semver；保存 schema/serializer version 和 content hash |
| Prompt | `prompt_id + prompt_version + output_schema_version`，内容不可变 |
| Model Assignment | `policy_version`，记录 endpoint/model/参数和流量比例 |
| QualityPolicy | 独立版本；Evaluator 与阈值一并冻结 |
| Golden Set | 不可变 dataset version；标注修改生成新版本 |
| Adapter | `adapter_name + contract_version + implementation_version` |
| 运行配置 | ConfigVersion 激活后不可变；Run 保存 PolicySnapshot hash |

不能通过复用同一版本号替换内容。发现错误时创建新版本，并用 `supersedes` 或迁移关系关联。

## 6. 分支与提交管理

### 6.1 分支模型

采用主干开发：

- `main` 始终保持可构建和可部署；
- 短生命周期功能分支使用 `feature/<issue>-<slug>`；
- 修复分支使用 `fix/<issue>-<slug>`；
- 发布候选使用不可变 tag，不长期维护 release 分支；
- 只在仍受支持的历史版本需要补丁时创建 `support/<major.minor>`；
- 紧急修复从当前生产 tag 创建，合并主干后再发布新 PATCH。

分支不得长期偏离主干；建议 1～3 个工作日内合并。大型能力通过兼容 Schema、功能开关和影子路径分步集成。

### 6.2 提交要求

- 每次提交只表达一个可审查意图；
- 提交信息包含类型、范围和 issue，例如 `feat(video): persist provider reconciliation state`；
- 生成文件必须能由已版本化工具复现；
- 不提交密钥、生产数据、个人信息、大媒体或本地环境路径；
- 数据库、API、合同、Prompt 或配置变更同时更新对应测试和文档；
- 提交签名和作者身份遵循组织安全策略。

### 6.3 Pull Request 门禁

合并至少要求：

1. 关联需求/缺陷和明确变更范围；
2. 风险、数据迁移、兼容性、成本和回滚说明；
3. 自动测试、静态检查、依赖/密钥扫描通过；
4. 代码所有者审批；P0 领域需双人审批；
5. API/合同/数据库变化有差分报告；
6. AI 行为变化有 Golden Set 对比，不仅给少量演示结果；
7. 用户可见变化同步更新用例、文档和发布说明。

作者不能作为唯一批准人。高风险变更按第 9 节进入增强审批。

## 7. 变更控制

### 7.1 变更类型

| 类型 | 示例 | 最低流程 |
|---|---|---|
| 标准变更 | 小型向后兼容功能、普通修复 | issue → PR → CI → 审批 |
| 重大变更 | 领域边界、存储、状态机、公开合同 | RFC → ADR → 设计评审 → 分阶段实施 |
| AI 行为变更 | Prompt、模型、参数、阈值、路由 | 离线评测 → 影子 → Canary → 扩量 |
| 数据变更 | Schema、迁移、保留期、回填 | 迁移评审 → 演练 → 监控 → 收缩 |
| 安全变更 | 权限、密钥、网络、敏感数据 | 威胁评审 → 安全审批 → 审计验证 |
| 紧急变更 | S0/S1 生产事件修复 | 事件授权 → 最小补丁 → 自动检查 → 上线 → 复盘 |

### 7.2 变更申请字段

- change_id、标题、发起人、业务理由；
- 影响需求、组件、合同、数据、项目和供应商；
- 风险等级、失败模式和安全影响；
- 实施步骤、测试证据、监控指标；
- 数据/应用/配置回滚路径和不可逆点；
- 计划窗口、责任人、审批人和客户通知；
- 完成结果、偏差和后续行动。

### 7.3 变更委员会

重大变更由产品、架构、研发、测试、运维、安全和模型质量代表共同评审。会议重点是证据与影响，不以会议本身替代自动校验。一般向后兼容修改不需要等待固定会议，可由授权审批者异步处理。

### 7.4 需求和设计同步

- FR/NFR 变更更新需求编号和追踪矩阵；
- 用例主路径改变时更新 API、测试和操作文档；
- 架构决策创建或替代 ADR，旧 ADR 保留状态；
- 删除字段或状态时保留兼容读取期，历史 Artifact 继续用原序列化器；
- 文档基线变化进入同一 PR，避免代码与规范分离。

## 8. CI/CD 与构建管理

### 8.1 CI 阶段

```text
源码与配置扫描
  → 格式/类型/单元测试
  → 合同与 Schema 兼容检查
  → PostgreSQL 迁移演练
  → 集成与核心 E2E
  → Golden Set 快速回归
  → 构建不可变镜像
  → SBOM/签名/来源证明
  → 候选仓库
```

任一阻断步骤失败不得产生“已批准”候选。构建只从受保护提交运行，依赖使用锁文件或 digest。

### 8.2 可复现构建

Release Manifest 至少记录：

- 产品版本、Git SHA、仓库状态；
- 构建器镜像 digest、工具链和依赖锁 hash；
- 前端静态资源和后端镜像 digest；
- OpenAPI、事件、Artifact 和数据库版本；
- 默认 Prompt、模型路由和 QualityPolicy 版本；
- SBOM、漏洞报告、签名和 provenance；
- 自动测试与批准记录。

同一源码与锁定环境应能重建语义等价制品；验证以 digest、签名和 Manifest 为准。

### 8.3 制品仓库

- 镜像、包和安装包进入不可变制品库；
- 生产部署只接受已签名、已批准 digest；
- `latest` 等可变标签不得作为生产部署依据；
- 保留当前生产、上一个稳定版和合同要求的历史版本；
- 删除遵循保留策略并保留审计事件。

## 9. 高风险配置项管理

### 9.1 数据库迁移

采用 `expand → backfill → dual-read/write 或 shadow-compare → switch → contract`：

1. Expand 阶段只增加向后兼容结构；
2. 回填具备检查点、限速、幂等和可观测性；
3. 新旧路径影子比对，差异不自动覆盖真实数据；
4. Switch 使用可回滚配置逐步切流；
5. Contract 仅在所有受支持应用不再读取旧结构、备份验证完成后执行。

进入共享环境的迁移文件不可修改。每个迁移声明预计时长、锁风险、空间增长、回滚/前滚方案和验证 SQL。

### 9.2 Prompt 与模型

Prompt 包含系统指令、模板、少样本、输入/输出 Schema、能力和安全约束。版本发布流程：

```text
草稿 → Schema 校验 → Golden Set 离线评测
     → 影子流量 → 小比例 Canary → 分阶段扩量 → 稳定
```

- 任何 Run 启动时冻结 Prompt/模型/参数/路由；
- 模型“同名更新”按新模型版本处理；
- 评估报告包含质量、失败率、延迟、成本和题材分层；
- 指标恶化自动停止扩量，并可恢复上一稳定 Assignment；
- 模型生成候选，不直接修改已发布权威对象或绕过程序 Gate。

### 9.3 QualityPolicy 与 Golden Set

- Gate 角色、Evaluator 版本、阈值、适用阶段和覆盖权限共同版本化；
- 硬门禁和业务风险项分开管理；
- 阈值变化必须报告误放/误拒及置信区间；
- Golden Set 训练部分与保留验收部分隔离；
- 标注修订创建新数据集版本，保留仲裁和差异记录；
- 旧运行按旧策略解释，不能用当前阈值重写历史结果。

### 9.4 Adapter 与供应商

- 领域只依赖版本化 Adapter 合同；
- H3 内部细节封装在 `VideoGenerationAdapter`，公共状态映射有合同测试；
- 能力参数变更先进入 Adapter 兼容层，不能把供应商字段扩散到 ShotContract；
- 供应商 operation_id、请求 hash、原始状态和收费状态可对账；
- Adapter 新版本需通过录制回放、沙箱和真实小流量验收。

### 9.5 权限与安全策略

- 角色/权限矩阵、RLS、对象存储签发、原始载荷访问和网络策略均视为代码；
- 权限扩大需要安全负责人审批和权限矩阵回归；
- 紧急临时授权有目的、范围、到期和审计，不形成长期隐性权限；
- 密钥轮换不改变业务配置版本内容，但记录 secret version 引用和验证结果。

## 10. 环境与运行配置

### 10.1 环境一致性

DEV、CI、QA、STAGING、PREPROD、PROD 使用相同容器和配置 Schema，通过显式值差异适配容量和端点。禁止在生产主机手工修改应用文件或容器内部状态。

### 10.2 四级配置治理

```text
PlatformDefault
  → TenantPolicy
    → ProjectProfile
      → RunSnapshot
```

- ConfigDefinition 声明类型、范围、依赖、敏感性和 apply_mode；
- 草稿经校验、Diff、审批和乐观锁后原子激活；
- requested 与 effective 分开保存，应用失败回滚 effective；
- 运行中任务只读 RunSnapshot，不被后续设置修改；
- 项目设置不得改变系统级安全下限和租户合同上限；
- 每个有效值可追溯到来源版本。

### 10.3 功能开关

功能开关用于兼容迁移、灰度和快速停止新路径，不用于永久隐藏未完成逻辑。每个开关需有所有者、默认值、作用域、建立时间、删除条件和最晚清理版本。

### 10.4 配置漂移

- IaC/部署控制器周期比对声明状态与运行状态；
- 检测到漂移时告警并记录，不直接覆盖未评估的生产状态；
- 紧急人工操作必须进入事件记录并在事后回归声明配置；
- 发布完成后存档 effective 配置 hash 和关键健康证据。

## 11. 发布管理

### 11.1 发布节奏

- 常规版本按固定窗口发布；
- 高风险数据库、权限和模型策略变化分开切流，避免同时改变多个失效面；
- 大版本先内部、试点租户、低风险租户再逐步扩展；
- 私有部署包与 SaaS 使用同一源码基线，差异由版本化部署 Profile 表达。

### 11.2 发布前检查

- 需求、ADR、风险和变更范围批准；
- 候选构建、签名、SBOM 和 provenance 验证；
- 测试文档规定的 P0/P1、Golden Set、性能、安全、恢复通过；
- 数据库 expand/backfill 已演练并估算生产窗口；
- 配置/Prompt/模型/QualityPolicy 版本冻结；
- 监控、告警、运行手册、值班和客户通知就绪；
- 应用、数据库、配置和模型路由回滚路径均已验证。

### 11.3 部署流程

```text
候选批准
  → 数据库兼容扩展
  → 内部环境验证
  → Canary 实例/租户
  → 自动健康与业务合成检查
  → 分批扩量
  → 稳定观察
  → 发布完成与基线归档
```

每一阶段有最大观察时间、自动停止条件和人工 Stop 权限。技术健康、业务 Gate、质量、成本和错误分类共同决定是否扩量。

### 11.4 回滚与前滚

- 应用通过旧 digest 回滚；
- 配置和 Assignment 激活上一稳定版本；
- Prompt/QualityPolicy 停止扩量并恢复旧版本；
- 数据库优先兼容前滚，禁止依赖破坏性降级；
- 已发布 Artifact 和交付包不回写，使用 supersedes 建立新版本；
- 回滚后验证队列、租约、Outbox、ProviderOperation 和对象引用一致性。

### 11.5 紧急修复

1. 事件负责人确认范围和临时缓解；
2. 从当前生产 tag 创建最小修复；
3. 至少完成受影响模块测试、迁移/回滚检查和一名独立审批；
4. 先 Canary 后扩量；
5. 合并回主干，24～72 小时内完成复盘、补齐测试和长期修复。

紧急状态不授权绕过租户隔离、硬交付门禁、审计和密钥保护。

## 12. 发布说明与兼容策略

每个版本发布说明包括：新增、修改、修复、已知问题、API/事件/Artifact 兼容、数据库迁移、配置变化、Prompt/模型/质量变化、安全公告、升级/回滚步骤和支持期限。

兼容原则：

- 新 Writer 上线前，旧 Reader 必须可安全忽略新增字段；
- 必填字段新增需要合同新版本或分阶段默认值；
- 枚举新增时消费者必须有 `UNKNOWN` 处理而不是错误映射；
- 删除字段先停止写入、观察读取、再在新 major 移除；
- 历史指纹使用原 contract/serializer version 验证；
- `/api/v2` 兼容层与 `/api/v3` 领域模型隔离并有退役时间表。

## 13. 审计、盘点与度量

### 13.1 配置状态记录

配置管理系统保存：配置项 ID、版本、状态、位置、所有者、创建/批准人、关联需求、构建/发布、部署环境、替代关系和保留期限。

### 13.2 定期盘点

- 每周：主干健康、失败门禁、依赖告警、过期功能开关；
- 每月：生产版本、配置漂移、权限、密钥轮换和备份恢复抽检；
- 每季度：受支持版本、Prompt/模型/质量策略、Golden Set 分布、供应商合同；
- 每次大版本：全量配置项和历史证书可验证性审计。

### 13.3 度量指标

| 指标 | 目标用途 |
|---|---|
| 变更前置时间 | 衡量交付效率，不鼓励绕过门禁 |
| 变更失败率 | 识别高风险组件和评审缺口 |
| 平均恢复时间 | 验证回滚、运行手册和观测质量 |
| 未计划配置漂移数 | 衡量环境一致性 |
| 迁移回滚/前滚成功率 | 衡量数据发布安全性 |
| Prompt/模型灰度撤回率 | 衡量离线评测有效性 |
| 构建可复现率 | 保障供应链和审计 |
| 过期功能开关数 | 控制长期复杂度 |
| 未追踪生产制品数 | 目标恒为 0 |

指标用于改进流程，不以减少缺陷上报量评价团队。

| 角色 | 职责 |
|---|---|
| 配置管理员/发布负责人 | 基线、候选、Manifest、发布和盘点 |

## 16. 例外管理

任何偏离本计划的行为都需记录 exception_id、理由、范围、风险、补偿措施、审批人和到期时间。例外到期自动进入复审，不能默认为永久规则。涉及租户隔离、密钥明文、审计删除、不可恢复数据操作或商业交付硬门禁的例外不得由普通项目审批授权。
