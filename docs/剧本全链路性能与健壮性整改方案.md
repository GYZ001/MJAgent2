> Shards、IR 合并、checkpoint 恢复、provider call gate、递归血缘保护、前端进度和真实双轨

## 1. 执行摘要

当前剧本链已经完成了以下正确方向的基础建设：

- 原文按 `SRC*` 建立稳定来源索引。
- Blueprint 已按连续 SRC 分片生成，并保存 raw/validated Artifact。
- 剧本模型输出紧凑 `ScreenplayGenerationIR`，后端确定性编译为完整 `EpisodeScreenplay`。
- IR 的来源遗漏、压缩不足和多地点场次已使用 `ScreenplayIRFidelityError` 类型化，不再通过错误文本匹配决定修复路径。
- 身份以 `identity.key`、`authority_id`、owned source evidence 为权威，不再以 display name 或角色词表猜测实体。
- `Issue.category` 开始区分 `structural / quality / operational`，AgentLoop 不再读取问题文本或错误码决定结构修复。
- 发布使用 `ScreenplayDocument + CompletionCertificate + ProductionRevision + input_fingerprint` 的不可变权威链。
- 剧本台正在收敛为纯剧本状态，不再混入分镜错误和分镜任务提示。

当前最大的系统问题不是“某一个 prompt 太长”，而是同一集被多个阶段重复理解：

1. 人物预检固定执行 current、future identity、coverage audit 三类调用。
2. Blueprint 分片完成后，还要执行两份全量语义审稿；有共识问题时再进入局部修复。
3. Baseline 再携带完整 Blueprint、Bible 投影、身份决议和完整 SRC，输出一份整集 IR。
4. IR 不完整时最多执行 32 轮保真补写。
5. Baseline 持久化后，若完整文档仍出现未知身份，又会回到人物发现模型。
6. Production Repair 可能继续执行大上下文 narrative patch。

整改后的最终原则是：

```text
只让模型做不可机械推导的语义决策；
同一语义只做一次；
格式恢复优先本地完成；
失败只重试最小单元；
完整 Document 建立后只有一个 working 权威；
最终发布合同和下游读取结构不改变。
```

## 3. 当前完整剧本链路

### 3.1 入口与 CAS 抢占

入口：

- `POST /api/episodes/{episode_id}/screenplay`
- `app.domain.screenplay_ops.start_screenplay`
- Capability：`screenplay.generate`

当前流程：

1. Capability/Preflight 检查当前状态和影响。
2. `_new_screenplay_recorder` 创建 `workflow_runs`。
3. `_spawn_screenplay_activation` 使用 `BEGIN IMMEDIATE` 和 `active_screenplay_run_id` CAS 抢占剧集。
4. 首次生成时清理旧未发布 IR、人物决议和兼容台词约束。
5. 注册 `task_registry` 后台任务。
6. `_screenplay_guarded` 获取集级文本生成槽位。

必须保留的不变量：

- 同一集只有一个 active screenplay owner。
- CAS、旧 IR 清理和新 Run 所有权切换必须在同一事务边界。
- spawn 失败必须恢复之前的 episode 状态和决议。
- 旧 worker 返回时必须检查 `active_screenplay_run_id`，不能覆盖新 owner。

### 3.2 人物发现

当前入口：

- `_recorded_screenplay_task`
- `_screenplay_character_discovery`
- `portraits.ensure_cards_for_text`
- `portraits.discover_character_candidates`

当前模型步骤：

1. current：扫描当前原文/草稿身份投影。
2. future identity：用未来章节窗口为当前称谓解析稳定真名。
3. coverage audit：再次审计遗漏人物或错误降级身份。
4. 新 named identity 进入 `ensure_character_card`，自动补文字卡但不在剧本阶段出图。
5. 功能身份和未来真名写入 `episodes.screenplay_character_resolutions`。
6. 人物谱可能增加 card，`bible_version` 和 workflow input fingerprint 随之刷新。

当前问题：

- current 已发现但 source label 不够精确时，候选可能被本地对齐丢弃，再由 coverage audit 用大 prompt 找回。
- coverage audit 无条件重复发送大量上下文。
- current/future/coverage 的成功结果没有统一的 normalized Artifact 作为恢复边界。
- 模型 HTTP 200 但 JSON 损坏时，当前阶段直接失败，不走内容级格式修复。
- 手工编辑发布和 repair-draft 仍可能调用同一套全量人物发现。

### 3.3 Blueprint

当前入口：

- `stages._generate_screenplay_narrative_blueprint`
- `stages._generate_sharded_narrative_blueprint`

当前机制：

1. 原文使用 `index_source_segments` 建立细粒度 SRC。
2. 默认每 28 个连续 SRC 生成一个 `NarrativeBlueprintShard`。
3. 每片携带上一片的 active facts、人物位置和最近节点。
4. 每片最多尝试 3 次；仍失败时自动二分。
5. raw 输出保存为 `screenplay_narrative_blueprint_shard_raw`。
6. validated 输出保存为 `screenplay_narrative_blueprint_shard`。
7. 全片合并后验证时间、空间、状态、决定、自主性、来源覆盖和顺序。
8. 程序确定性生成 `scene_plans`。

这是当前链路中最成熟的分片实现，整改应复用其设计：

- source hash
- boundary hash
- raw/normalized 分层
- 自适应二分
- 本地复用
- 先局部校验、后全局校验

### 3.4 Blueprint 语义审稿

当前入口：

- `stages._semantic_review_narrative_blueprint`

当前机制：

1. 每轮生成两个独立语义审稿结果。
2. 每份审稿携带完整 Blueprint 和完整带 ID 原文。
3. 两份审稿对同一 code + node_keys 达成共识才进入修复。
4. 修复由 `_repair_narrative_blueprint` 在局部节点闭包中执行。
5. 最多 6 轮语义复审。
6. 共识 Artifact 按 Blueprint hash 复用。

当前问题：

- 同一轮的两个 reviewer 当前串行执行。
- 即使只有少数高风险节点，也发送完整 Blueprint 和完整来源。
- 两份 reviewer 都不可用时会记录无共识并直接继续，可靠性语义不够明确。
- 语义复审和局部修复的最大轮数较大，长尾时延明显。

### 3.5 整版 IR Baseline

当前入口：

- `stages.generate_screenplay`
- `stages.generate_screenplay_baseline`
- `_run_with_agent_loop`

当前模型输入：

- 完整 Blueprint 和 `scene_plans`
- 当前来源相关 Bible 投影
- 人物身份预解析合同
- 带稳定 ID 的完整原文
- 保真预算
- 全局 metadata、experience 和 scenes/units 输出合同

当前输出：

- `ScreenplayGenerationIR`
- metadata
- identities
- scenes/units
- experience

当前机制：

- Baseline 只允许一次完整模型响应。
- raw 和 normalized IR 分层持久化。
- JSON/Schema 和编译问题通过 typed `Issue.category=structural` 控制 AgentLoop。
- 质量问题通过 `Issue.category=quality` 交给后续完整文档 QA。
- `ScreenplayIRIdentityConflictError` 进入条件式 AI 身份仲裁。
- `ScreenplayIRFidelityError` 进入来源缺口补写。
- 其余编译错误作为 `SCREENPLAY_IR_COMPILE_FAILED` structural Issue。

### 3.6 IR 身份仲裁

当前入口：

- `identity_adjudication.adjudicate_screenplay_ir_identities`

当前正确机制：

- 精确 authority 先由程序绑定。
- 未引用 identities 先删除。
- AI 只看发生冲突的 identity、owned source IDs、相关来源段和 authority registry。
- 决议只能引用该 identity 自己拥有的来源段。
- `bind` 只能引用现有 authority。
- `new_functional` 由后端生成稳定 authority ID。
- 同一 display name 的多个实体可以共存。
- 只有引用处使用了歧义 display name 而不是唯一 identity key 时才失败。

需要保持：

- 不按姓名、职业、年龄、服饰、称号或题材分类人物。
- 不用 display name 唯一性代替实体唯一性。
- 不允许两个不同 identity 因共享称谓而合并。

### 3.7 IR 保真补写与编译

当前入口：

- `_complete_screenplay_ir_fidelity`
- `compile_screenplay_ir`

当前过程：

1. 尝试完整编译。
2. 只捕获 `ScreenplayIRFidelityError`。
3. 计算遗漏 SRC 和低密度窗口。
4. 依据 Blueprint 选择受影响 scene plans。
5. 模型只输出 `new_scenes` 或 `insertions`。
6. 后端重新编号 event key 并合并。
7. 再次全局编译。
8. 最多循环 32 轮。

编译器最终确定性生成：

- events
- beats/plot spine
- source coverage
- dialogue chains
- full script text
- information ledger
- voice bible
- complete narrative plan
- stable IDs 和双向引用

当前问题：

- 最大 32 轮过大。
- 保真 patch 没有基于缺口数量动态限制总轮次。
- format error 和“插入 0 个 unit”的语义失败仍混在同一轮预算。
- 当前整版 Baseline 的一次大响应导致 20.7% 的 Schema/编译硬失败。

### 3.8 完整 Document Baseline 与 Production Repair

当前入口：

- `production.screenplay_repair.run_screenplay_production`

当前过程：

1. 计算完整 authority fingerprint。
2. 创建/恢复 `ProductionRevision`。
3. 签发 Production Grant。
4. 首次生成完整 `EpisodeScreenplay`。
5. 按剧情和口播容量扩展 target duration。
6. 转换并持久化一个 `screenplay_document` candidate。
7. 只在完整 Document 建立后调用一次 `mark_baseline_generated`。
8. 重新应用人物决议、voice 归一化和 narrative graph 归一化。
9. 执行完整 QA。
10. `must_fix/runtime_blocking` Issue 进入有限局部 Patch。
11. score-only 质量问题记录但不伪装成 runtime gate。
12. 所有 runtime gate 通过后签发证书并原子发布。

必须保持：

- shard 或 IR 中间产物不能成为 `working_screenplay_artifact_id`。
- `baseline_generation_count` 只统计完整 Document Baseline。
- QA 后禁止完整重生和根对象替换。
- Patch 必须 CAS 到完整 Document 链头。

### 3.9 发布、剧本台和下游

发布：

- `production.publish.publish_screenplay`
- `production.certificate`
- `production.revision.set_published_artifact`

最终权威：

- approved `screenplay_document`
- `episodes.screenplay_json` 的 `EpisodeScreenplay` 投影
- consumed Completion Certificate
- published Production Revision
- exact input fingerprint

下游：

- 剧本台读取 `EpisodeScreenplay` 投影。
- 人工草稿也编辑完整 `EpisodeScreenplay`。
- Review Wall 比较 Document 投影、页面投影、证书和 revision。
- 分镜通过 `resolve_downstream_screenplay` 获取唯一不可变剧本。
- 视频计划消费 narrative plan 中的 actions、state、identity contracts。

最终公开结构不得因本次性能整改改变。

## 4. 目标架构

### 4.1 总体链路

```text
S0  请求预检与 CAS Run 抢占
S1  当前集人物提取
S2  未决身份的定向后文消歧
S3  Blueprint SRC 分片生成
S4  风险节点语义复审
S5  全局 Screenplay Envelope
S6  Blueprint-owned 场次写作分片
S7  分片合并为完整 ScreenplayGenerationIR
S8  身份精确绑定与条件式仲裁
S9  全局来源/场次/保真编译门禁
S10  一次性编译为 EpisodeScreenplay
S11  一次性建立 ScreenplayDocument Baseline
S12  完整文档 QA 与有限 Patch
S13  Completion Certificate 与原子发布
S14  剧本台和下游读取已发布权威
```

### 4.2 核心边界

分片只存在于完整 Document Baseline 之前：

```text
Blueprint Artifact
  ├─ Identity Discovery Artifact
  ├─ Envelope Artifact
  ├─ Scene Shard 1 Artifact
  ├─ Scene Shard 2 Artifact
  └─ Scene Shard N Artifact
       ↓
Merged ScreenplayGenerationIR Artifact
       ↓
Compiled ScreenplayDocument Baseline
       ↓
Document Patch Chain
       ↓
Published ScreenplayDocument
```

一旦完整 `screenplay_document` 创建：

- 所有后续修改只走现有 Document Patch。
- 不回写历史 scene shard。
- 不同时维护 shard working head 和 Document working head。
- `working_screenplay_artifact_id` 永远只指完整 Document。

## 5. 目标内部数据合同

### 5.1 ScreenplayEnvelopeIR

用于承载整集全局语义，不由各场 shard 重复生成：

```json
{
  "contract_version": "screenplay-envelope.v1",
  "episode_no": 1,
  "metadata": {
    "title": "",
    "logline": "",
    "dramatic_question": "",
    "protagonist_goal": "",
    "obstacle": "",
    "stakes": "",
    "emotional_curve": "",
    "ending_hook": "",
    "source_basis": "",
    "adaptation_direction": "",
    "opening": "",
    "development": "",
    "conflict": "",
    "climax": "",
    "episode_premise": "",
    "approved_adaptations": [],
    "forbidden_additions": []
  },
  "experience": {
    "director_objective": "",
    "satisfaction_criteria": "",
    "required_processing_s": 1.0,
    "forbidden_misconceptions": []
  },
  "blueprint_hash": "sha256",
  "identity_registry_hash": "sha256"
}
```

输入只需要：

- episode 元数据
- Blueprint 节点摘要和 arc/decision/agency 关系
- 已冻结 identity registry 摘要
- 不需要再次发送完整原文

### 5.2 ScreenplaySceneShardPlan

由程序根据 `scene_plans`、来源规模和预计输出复杂度确定性生成：

```json
{
  "shard_id": "SS001",
  "scene_plan_keys": ["bp-sc001", "bp-sc002"],
  "source_segment_ids": ["SRC0001", "SRC0002"],
  "estimated_units": 18,
  "estimated_output_chars": 9000,
  "boundary_state_in": {},
  "boundary_state_out": {},
  "source_hash": "sha256",
  "boundary_hash": "sha256",
  "blueprint_hash": "sha256",
  "identity_registry_hash": "sha256"
}
```

分组规则不按固定场数：

- 连续 scene plans 才能进入同一 shard。
- 目标单位数：16~24 units。
- 预计 JSON 字符：5k~12k。
- 单个 scene 自身超过目标时允许独占一个 shard。
- 不切开一个 Blueprint scene plan。
- 不跨时间域倒序组合。

### 5.3 ScreenplaySceneShardIR

```json
{
  "contract_version": "screenplay-scene-shard.v1",
  "episode_no": 1,
  "shard_id": "SS001",
  "scene_plan_keys": ["bp-sc001", "bp-sc002"],
  "scenes": [
    {
      "key": "bp-sc001",
      "scene_heading": "【场1】日 / 地点",
      "story_function": "",
      "summary": "",
      "conflict": "",
      "turn": "",
      "character_keys": ["identity-key"],
      "entry_state": "",
      "exit_state": "",
      "context_requirements": [],
      "units": [
        {
          "kind": "action",
          "text": "",
          "event_key": "local-event-1",
          "source_segment_ids": ["SRC0001"],
          "resulting_state": ""
        }
      ]
    }
  ],
  "consumed_source_ids": ["SRC0001"],
  "unresolved_participants": []
}
```

约束：

- scene key/heading/order 由 Blueprint 所有。
- 每个 unit 只能使用本 shard scene plan 允许的 SRC。
- speaker key 只能引用已冻结 identity key。
- 不输出 metadata、experience、events、beats、coverage 或最终编号。
- 不允许 shard 自行生成 authority ID。
- 发现未知身份时输出 typed `unresolved_participants`，不得自行发明实体。

### 5.4 Merged ScreenplayGenerationIR

程序执行：

```text
Envelope.metadata
+ IdentityRegistry.identities
+ 按 shard plan 顺序拼接的 scenes
+ Envelope.experience
= 完整 ScreenplayGenerationIR
```

合并后必须重新执行：

- 所有 scene plan 是否恰好存在一次。
- scene 顺序是否与 Blueprint 完全一致。
- source ID 是否属于对应 plan。
- 所有非标题 SRC 是否被正文 unit 消费。
- 首次来源所有权顺序是否单调。
- event key、chain key、scene key 是否全局唯一。
- speaker key 是否存在。
- boundary state 是否与相邻 shard 一致。

## 9. 重试与失败矩阵

| 失败类型 | 识别方式 | 自动动作 | 最大次数 | 复用范围 |
|---|---|---|---:|---|

| 用户取消 | CancelledError | 保留或清理按阶段决定 | 0 | checkpoint |
| 服务重启 | PAUSED_EXTERNAL | 自动恢复缺失步骤 | 0 新语义轮 | validated Artifact |

## 10. 并发与资源调度

### 10.1 两层门

```text
Workflow Gate
  控制同时活跃的剧本/分镜集数

Provider Call Gate
  控制真实并发文本请求数
```

### 10.2 单集并发

- Blueprint shard 因边界事实依赖，保持顺序生成。
- 两份 Blueprint reviewer 可以并行。
- Scene writing shards 在 Blueprint 和 identity registry 冻结后允许并行 2。
- Envelope 可与首批 Scene Shard 并行，但 Merge 必须等待全部完成。
- Document QA/Patch 保持串行 CAS。

### 10.3 防止请求风暴

当 `text_generation_concurrency=10`：

- 全系统最多 10 个真实文本 provider call。
- 一集最多占 2 个 Scene Shard call。
- batch 优先级低于 interactive。
- recovery 低于 interactive、高于 batch 或按现有优先级保持。

```text

  ↓
character discovery raw
  ↓
character discovery normalized
  ↓

  ↓
Blueprint validated
  ↓

  ↓

  ├─ Envelope raw → Envelope validated
  ├─ Scene shard raw → Scene shard validated
  └─ ...
  ↓
Merged IR
  ↓
Fidelity patch raw/validated
  ↓
Completed IR
  ↓
ScreenplayDocument Baseline
  ↓
Document Patch Chain
  ↓
Published ScreenplayDocument
  ↓
Certificate / Page Projection / Storyboard
```

清理时：

- 只删除当前失败 Run 且不在 published ancestry 中的 IR。
- 已发布 Document 的所有递归祖先保留。
- raw provider logs/error logs 可保留审计，但不能用于业务恢复。
- normalized validated Artifact 才能复用。

## 15. 风险与控制

| 风险 | 影响 | 控制 |
|---|---|---|
| 分片导致跨场语义断裂 | 内容质量下降 | Blueprint state/decision/agency 边界；合并后全图编译和 QA |
| 调用数增加抵消时延收益 | 总时间上升 | 动态 3~4 shard；并行 2；真实 call gate；A/B 门槛 |
| shard 身份 key 漂移 | 分镜身份错误 | 冻结 identity registry；未知 participant typed 返回 |
| 同名不同实体误合并 | 叙事错误 | authority ID + identity key；display name 不参与实体合并 |
| Bible 在并发集间变化 | 指纹漂移 | 现有 card/Bible lock；身份阶段结束后刷新 fingerprint |
| malformed HTTP 200 被缓存 | 永久重复坏输出 | 仅 validated Artifact 业务复用；format attempt 使用新 semantic attempt |
| 未完成 Baseline 无法续跑 | 重复付费 | checkpoint 保存每个 shard；新增 can_resume_baseline |
| 清理删除已发布祖先 | 证据链断裂 | 递归 ancestry 保护 |
| 旧文档与当前代码冲突 | 实施偏差 | 同步更新 Prompt Spec、分阶段文档、Runbook |
| 过早上线候选 | 质量回退 | 双轨、盲评、性能门槛全部通过后切换 |

## 16. 回滚策略

开发阶段允许清空测试数据，但实现仍使用开关：

```text
screenplay_scene_shards_enabled
screenplay_targeted_identity_enabled
screenplay_targeted_blueprint_review_enabled
```

回滚原则：

- 关闭 Scene Shards 后，仍可走当前完整 IR Baseline。
- 关闭 targeted identity 后，回到 current/future/coverage 旧路径。
- 关闭 targeted Blueprint review 后，回到完整双审稿。
- 不删除 Artifact、Run、provider call 或证书记录。
- 已发布 Document 不因回滚失效。
- 任何回滚都不得把 scene shard 直接提升为 published Document。
