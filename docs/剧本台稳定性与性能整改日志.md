### 已定位的性能缺陷（待 RCA 确认后修复）

- **P-1**：`_screenplay_ready` 在每次状态轮询里对不可变的已发布权威链做**完整重验证**
  （重解析 2 MB Artifact、深拷贝 pydantic 模型、重编译 IR、重算 content_hash、重验证书）。
  轮询间隔运行中 2 s / 终态 15 s ⇒ 单个用户停留在剧本台就持续占用约 13% CPU。
  与 `debug-backend-unresponsive.md` 记录的「同步 CPU 任务阻塞事件循环」是同一类问题。
- **P-2**：`screenplay_from_artifact_record` 已有模型缓存，但每次命中都
  `model_copy(deep=True)` 一份 2 MB 模型（32,460 次 deepcopy / 次调用），占总耗时 52%。
- **P-3**：`view=script` 返回 1.6 MB 的 `narrative_plan`，前端零使用。
- **P-4**：`recover_screenplay_tasks()` 在**每次后端启动**时对所有 ready/failed 集逐集跑
  同一套完整重验证；O(N × 2.5 s)。
- **P-5**：`_episode_or_404` 用 `SELECT *` 读整行，轻量状态端点也要读出 1.9 MB 的
  `screenplay_json`。
- **P-6**：前端草稿自动保存把整份剧本（含 1.6 MB `narrative_plan`）
  `JSON.stringify` 后同步写 `localStorage`，且 650 ms 去抖后整体 PUT 上传；
  接近 5 MB 配额，多集草稿会触发同步 `QuotaExceededError`。

## Round 0（2026-08-22 05:10）· 历史证据 RCA（未运行新一轮生成）

对上一轮串行运行（`logs/serial_run13.log`、`logs/serial_loop2.log`）留下的
`error_logs` / `provider_calls` 做取证，得到三个可复现的根因。

### 根因 R1 —— `max_tokens` 被当作「正文预算」，而供应商把 reasoning 计入同一预算

**失败位置**：`app/hiagent.py::_reject_truncated_chat_response`
（`ProviderError(OUTPUT_TRUNCATED, retryable=False, replay_safe=False)`），
经 `screenplay_scene_shards.py::execute_review` → `model_gateway.chat_structured` 抛出，
整集 `SCENE_SHARD_GENERATION` 阶段失败。
证据：`ERR-20260822-83b38b`、`ERR-20260822-63a69b`
（`finish_reason=length, reasoning_present=True, completion_tokens=2049`，max_tokens=2048）。

**输入与程序状态**：`_scene_shard_semantic_review_budget` 用
`screenplay_scene_semantic_review_required_tokens()` 从「最坏情况答案 JSON」估算
`required`，1–2 个 unit 时取下限常量 `SCREENPLAY_SCENE_SEMANTIC_REVIEW_MIN_OUTPUT_TOKENS = 2048`，
然后 `max_tokens=int(budget["required"])`。

**日志证据（全量统计，2767 次成功 chat 调用的 usage）**：

| 阶段 | n | completion p50 | reasoning p50 | reasoning/completion p50 |
|------|---|----------------|---------------|--------------------------|
| `screenplay_scene_shard_semantic_review` | 371 | 5186 | 5088 | **0.97** |
| `screenplay_character_discovery` | 68 | 2779 | 2490 | 0.89 |
| `screenplay_scene_shard_semantic_repair` | 38 | 1911 | 1689 | 0.86 |
| `narrative_graph_patch` | 36 | 4756 | 3977 | 0.84 |
| `screenplay_blueprint_review` | 19 | 9128 | 8415 | 0.92 |

全体 reasoning 分位：p90 4436 / p95 6849 / p99 10859 / max 21959。
一次成功的 review 调用实测：`completion_tokens=1417`，其中 `reasoning_tokens=1328`，
`message.content` 只有 235 字符。**答案约占 3%，思考占 97%。**

**为什么现有设计允许它发生**：预算计算只建模了「答案要多大」，而
`_reject_truncated_chat_response` 的注释本身就写着 reasoning 与 content 共用 `max_tokens`。
两处认知没有连起来：每个阶段各自把常量往上调（`BLUEPRINT_REVIEW_MAX_TOKENS` 从 8192
调到 16384、`IR_FIDELITY_PATCH_MAX_TOKENS=16384` 的注释已经点破原因），
但没有任何一层把「reasoning 开销是模型属性」这件事收口。

**偶发还是必然**：必然的**分布性**失败。24/2767 ≈ 0.87% 的调用 `completion == max_tokens+1`
（即被截断，且因为截断发生在记录之后，这些行仍是 `status='OK'`，
所以按 `error` 文本统计截断率会得到 0，具有欺骗性）。
一集要打约 150 次这类调用 ⇒ 单集不被截断的概率 ≈ 0.991^150 ≈ **26%**。
这与「前 10 集几乎每轮都挂」完全吻合。

**同模式的其它风险路径**：所有从「答案大小」推 `max_tokens` 的地方
（`screenplay_scene_semantic_repair_required_tokens`、`screenplay_ir_token_budget`、
`BLUEPRINT_REVIEW_MAX_TOKENS`、`narrative_graph_patch` 的 8192 常量）全部同病。

**应在哪一层解决**：`app/hiagent.py::text_request_token_limits` —— 它是
所有文本调用把「请求预算」换算成「供应商 max_tokens」的唯一入口，
也是 operation_id 指纹与蓝图 token 预算共用的同一函数。
reasoning 开销是 provider/model 属性，不是每个调用点的属性。

### 根因 R2 —— retry grant 与 revision 的绑定存在两份真源，rebase 后必然失配

**失败位置**：`app/stages.py::_commit_blueprint_authority_checkpoint`
→ `[BLUEPRINT_RESOLUTION_GRANT_INVALID] pinned retry grant失效`（`ERR-20260822-14fbf4`，EP4）。

**日志证据**：run `run_50e9863f1ee5` 的 `config_snapshot_json` 钉住
`blueprint_retry_grant_id = pgrant_47209e7a9ac3`；该 grant 行的
`production_revision_id = rev_7bb707e0a75d`，而 `rev_7bb707e0a75d.status = 'superseded'`。
校验 SQL 要求 `production_grants.production_revision_id = 当前 active revision.id`，
因此必然查不到。

**为什么现有设计允许它发生**：
`ensure_production_revision()` 在新建 revision 时会把 `grant_id` 带到新行
（正是上一轮为修 “GRANT_DRIFT” 加的），但**没有反向更新 `production_grants` 行**。
于是同一份授权关系被存在两处：`production_revisions.grant_id`（已跟着 rebase 走）
与 `production_grants.production_revision_id`（停留在旧 revision）。
`_commit_blueprint_authority_checkpoint` 同时校验两处 ⇒ 合法 rebase 之后必然自相矛盾。

**偶发还是必然**：只要「上次结果未知 ⇒ 签发 retry grant」之后运行内又发生一次
合法的 revision 重建，就 100% 触发。

**应在哪一层解决**：`app/production/revision.py::ensure_production_revision`
的同一事务里把 grant 行改绑到新 revision —— 让「授权属于哪条 revision」只有一个真源。

### 根因 R3 —— 身份契约用自然语言 `source_label` 当主键，退化称谓一次即致命

**失败位置**：`app/portraits.py` current identity 投影校验
`source_label 重复：人` / `current 同一 source_label 对应多个 identity_group：人`
（`ERR-20260822-ae7fb7`，EP4）。

**证据**：provider call 5029 的 `f` 数组 12 条，source_label 依次为
`精明的男子 / 靠山老祖 / 外宗弟子 / 人 / 观望之人 / 师兄 / 人 / 外宗弟子 / 老者 / 男子 / 女子 / 小胖子`
—— `人` 与 `外宗弟子` 各出现两次且指向不同 `functional_identity_key`。
同一批次的另一次采样（call 5024）给出的是可区分的
`一个外宗弟子 / 一位凝气二三层的师兄`，说明这是采样波动而非输入必然。

**为什么现有设计允许它发生**：`screenplay_character_discovery` 的身份子阶段在
`model_gateway.chat_structured` 里被硬性要求 `format_retry_limit == 0 且 semantic_retry_limit == 0`
（“forbids structured retries”），`_identity_structured_with_resample` 也只对
「供应商未送达」重采样。所以一次退化采样直接杀死整集，没有任何有界纠正机会。

**状态**：**暂不修改**。这一条与上一轮已记录的「绿袍修士 / 韩宗」刻意 fail-closed
是同一族问题，需要先确认它在串行、且 R1 修复后是否仍然复现，再决定是否引入
「严格细化式」有界修复（要求修复后的答案除碰撞标签外与原答案逐项一致）。
先记录，不提前设计。

## Round 1（2026-08-22 06:20）· 静态分析与基线测量期间发现的缺陷

### 根因 R4 —— 剧本台的两个端点对同一集给出互相矛盾的权威状态

**失败位置**：`app/domain/storyboard_ops.py::episode_detail`。

**证据**（在**未改动**的运行中后端上实测，同一时刻同一集）：

```
GET /api/episodes/ep_3d523ff4d0a4/screenplay/status   -> screenplay_state.code = ready_storyboard_empty
GET /api/episodes/ep_3d523ff4d0a4?view=script         -> screenplay_state.code = qa_certificate_invalid
```

**输入与程序状态**：`episode_detail` 在第 4441 行 `ep.pop("screenplay_json", None)`
（避免把整份投影回传前端），而 `screenplay_state` 在第 4509 行才计算。
`_screenplay_ready(ep)` 的第一道判定就是
`if not (screenplay_json and status == "ready"): return False`
—— 投影已被 pop 掉 ⇒ 恒为 False ⇒ 恒走 `qa_certificate_invalid` 分支。

**为什么现有设计允许它发生**：权威判定函数接收的是「即将返回给前端的字典」，
而不是「数据库里的那一行」。这个字典在返回前被逐字段裁剪，于是**裁剪顺序**
悄悄决定了权威判定的结果。两个端点各自裁剪、各自判定，没有任何一处保证它们一致。

**偶发还是必然**：必然。任何 `ready` 集通过 `view=script` 读取都会拿到错误状态。
剧本台的 `useScriptEpisode` 恰好把 detail 与 light status 合并
（`{...full, ...light}`，且只在 light 更新时间不早于 full 时才覆盖），
所以平时被轻量状态遮住；一旦 light 落后或失败，页面就会错误地提示
「上游版本已变化，需重新校验剧本」并给出错误的主操作。

**同模式的其它风险路径**：`episode_detail` 里所有「先裁剪后判定」的字段。

**修复**：把「回传投影」和「判定用的行」分开——pop 出来的值显式传给
`_screenplay_authority_state`，页面响应体依旧不含 `screenplay_json`。

**附带的性能影响**：修复前 `episode_detail` 因为提前 fail-closed，会转而执行
`_published_screenplay_revalidation_eligibility` 这条**恢复**路径；修复后走正常
权威校验路径。两者都不便宜，但只有后者是正确答案。

### 前端（`frontend/src/pages/ScriptPage.tsx` + `App.tsx`）

首屏请求（并发发起，依赖顺序如下）：

```
/api/session            领取本机会话密钥（除 health/session 外所有 /api/* 强制校验）
/api/settings           模型/并发等运行参数
/api/projects           项目列表（侧栏）
/api/projects/{pid}?view=picker&episode_limit=1&episode_cursor=…   Agent 上下文标签
/api/projects/{pid}?view=picker&episode_limit=60&episode_cursor=…  分集选择器窗口

/api/episodes/{eid}/screenplay/status                              轻量状态（详情落地后才启动轮询）
/api/episodes/{eid}/screenplay/draft                               云端草稿恢复
```

状态管理：`useScriptEpisode` = `useEpisode(view="script", interval=0)`（只在挂载/手动
刷新时拉一次）+ `usePoll(status, active?2s:15s)`；两者按
`screenplay_updated_at` 新旧合并成一个 `Episode`。编辑态是本地 `draft`
（深拷贝自 `ep.screenplay`），650 ms 防抖后同时写 localStorage 与
`PUT /screenplay/draft`；发布走 `PUT /episodes/{id}/screenplay`（带 `expected_version` CAS）。

### 后端生成链

```
POST /episodes/{id}/screenplay
  └ ui_route("screenplay.generate")          Command Bus（可能要二次批准）
  └ resolve_screenplay_resume_eligibility()  决定 baseline / baseline_rebuild / finalize
  └ _spawn_screenplay_activation()           BEGIN IMMEDIATE 事务里一次性完成：
        · 抢占该集所有权（CAS active_screenplay_run_id）
        · 需要时 rebase revision
        · 蓝图未决回执预算判定 / 必要时签发 retry Production Grant
        · 注册进程内任务（task_registry）
  └ _recorded_screenplay_task(recorder)      WorkflowRun / StepRun / RunEvent 留痕
        ├ step character_discovery → app/portraits.py 身份发现（current / future / 结构化覆盖）
        └ step screenplay_document → _screenplay_task → run_screenplay_production
              ├ ensure_production_revision + Production Grant
              ├ generate_screenplay_baseline (app/stages.py)
              │     BLUEPRINT_GENERATION   时空因果蓝图，按 leaf 分片、有界重试/拆分
              │     IDENTITY_FREEZE        冻结身份注册表（含 reference 类归属）
              │     ENVELOPE_GENERATION    全局包络
              │     SCENE_SHARD_GENERATION 场次写作 + 语义审查 + 语义修复（app/screenplay_scene_shards.py）
              │     IR_MERGE               合并 IR → compile_screenplay_ir → EpisodeScreenplay
              ├ STRUCTURE_VALIDATION       run_screenplay_qa + Production Repair Agent 局部修复
              ├ QUALITY_SCORING            evaluation（score_only）
              └ PUBLISHING                 签发并消费 completion certificate，原子写
                                            episodes.screenplay_json + screenplay_artifact_id
```

### 核心数据关系

- `episodes` 是**投影**：`screenplay_json`（页面用）、`screenplay_artifact_id`
  （= `published_screenplay_artifact_id`）、`screenplay_production_revision_id`、
  `screenplay_completion_certificate_id`。
- `production_revisions` 是**生产账本**：一次 revision 只允许一次 Baseline，
  `checkpoint_json` 保存 phase / 各 shard 状态 / 已用修复策略 / open issues；
  `grant_id` 指向授权。
- `artifacts` 是**不可变证据**：blueprint / identity_registry / envelope /
  scene_shard / merged IR / screenplay_document，按 `content_hash` 封印、按
  `parent_artifact_ids` 形成血缘。
- `completion_certificates` 绑定 (artifact_id, artifact_hash, input_fingerprint,
  contract_version, qa_profile_version, revision_id)，发布时被消费。
- 读取侧 `resolve_current_screenplay_authority()` 把上面全部重新校验一遍，
  任何一处漂移即 fail-closed。

### 并发与事务边界

- `text_generation_concurrency = 10`：同时作用于「文本工作流槽位」与
  「真实 provider 调用槽位」（`app/generation_concurrency.py`）。
  串行模式下只有一集在跑，但该集内部的场次分片仍可并发占满 10 个 provider 槽位。
- 每次真实调用在租约内执行；租约内看到异常会触发批次 fail-fast 中止。
- 写事务一律 `BEGIN IMMEDIATE` + CAS（激活、revision、certificate、publish），
  SQLite WAL，异步写走 `run_write_transaction` 的有界重试。

##### 根因 R5 —— 逗号切分出的从属子句被要求「独立成画」，合同无解

**失败位置**：`app/screenplay_scene_shards.py:5805`（创作语义门禁 3 轮修复后仍未收口）。

**实测证据**（两位独立审查员 call #5427 / #5428 的原始 finding）：

| unit | 冻结源文 | 模型写的画面 | 双审共识 |
|------|---------|------------|---------|
| `SRC0012:unit:003` | 「但他性格坚毅，」 | 「山林间一片寂静，云雾缓缓流动。」 | `source_contradiction` |
| `SRC0014:unit:008` | 「可在看到带着孟浩走来的绿袍男子后，」 | 「绿袍男子带着孟浩走来。」 | `source_contradiction` + `unsupported_action` |

**输入与程序状态**：`app/source_facts.py:24`
`ACTION_CLAUSE_BOUNDARIES = frozenset("。！？!?；;：:，,\n\r")` —— **按逗号切分**。
中文一个句子内部用逗号连接多个从句，于是切出来的 unit 大量是**语法上不能独立**的成分：

```
SRC0012  这一幕落在孟浩眼中，/ 让他忽然觉得…美好，/ 但他性格坚毅，/ 此刻深吸口气，/ 倒也没有多言。
SRC0014  …/ 神色带着冷淡，/ 可在看到带着孟浩走来的绿袍男子后，/ 他站起身…抱拳一拜。
```

而场次写作合同（`app/screenplay_scene_shards.py:4224`）明确规定
「每个 slot 只能改写自身 source_fact，不得借用相邻 unit 的事实」，
语义审查合同（同文件 4726 行）同样规定「不能借用其他 slot 的 source_fact 来判定当前 slot」。
**同一条隔离规则，既让从属子句成为独立画面 slot，又让它无法被合法渲染。**

进一步取证蓝图的分类（artifact `art_baf51056090e`）：
- `SRC0012:unit:003` 被放进 `environment_source_unit_keys`（纯环境），
  而同一句的 001/002/004/005 都归给了 孟浩 的 state_subject。
  可是环境 slot 的合同是「不得写入任何人物的思考、发问、反应、动作或情绪」，
  源文却整句都是人物内在特质 ⇒ **写环境就与源文矛盾，写人物就是 environment_personification**，
  两条路都通不过，**可证明无解**。
- `SRC0014:unit:008` 被冻结为 绿袍男子 的 `state_subject`/`visible`，模型据此写出
  「绿袍男子带着孟浩走来」——**完全符合冻结权威**，却仍被审查员以
  「把时间状语从句改写成主动作陈述」判为矛盾：审查员在**重新审判冻结权威本身**。

**为什么现有设计允许它发生**：这类错误**只能在蓝图阶段修**（重新分类），
却**只在场次语义阶段被发现**（第 N+2 阶段），而那里唯一可用的补救手段是重写文案——
重写文案永远修不好一个分类错误。3 轮修复因此每轮得到完全相同的判定。

**偶发还是必然**：**取决于蓝图采样**。同一集在今天早些时候曾用另一份蓝图成功发布过；
本次这份蓝图的分类恰好落在无解组合上。SS002 在历史上累计已发生 **254 次 provider 调用**、
整片重写 8 次，全部停在同一道门——证明「重摇场次分片」无法解决，绑定约束在蓝图。

**同模式的其它风险路径**：上一轮记录的根因 10/B（`SRC0020:008` 木牌上的「杂」字）
属于同一族——源 unit 既不是人物状态也不是纯环境。

##### 已证伪的假设（本轮新增，避免后人重走）

**假设：可以用确定性程序判定「某个 unit 是不是在讲人」，从而在蓝图阶段拦截误分类。**

**修复层次的选择**：不能在场次层修（它唯一的手段是重写文案，修不好分类错误），

  必须写进该人物的 state_subject 证据，不得放进 `environment_source_unit_keys`。
- `app/stages.py::_generate_screenplay_narrative_blueprint`
  带反馈重建时**跳过**「同 input_fingerprint 复用上一版蓝图」的短路——
  那份蓝图正是死结的来源。
- `_append_blueprint_semantic_rebuild_event` 留下 durable 证据（`BLUEPRINT_SEMANTIC_REBUILD`）。

**为什么这不是「盲目重试」**：重建携带具体证据、改变了缓存键、并把约束写进提示词；
且严格限一次——真正无解的输入不会因为多试几次而变得有解。

**回归**：`tests/test_blueprint_semantic_rebuild.py`（11 例）覆盖

source_hash 必须改变、提示词约束的出现与不出现、重建预算有界、

## Round 3 · 冻结前代码审查发现并修复的两个缺陷（2026-08-22 18:20）

派 subagent 对本轮全部后端改动（`git diff d4aafef -- app/`，约 800 行）做只读审查，
它证实了缓存键完整性、锁覆盖、contextvar 线程隔离、grant 改绑事务一致性、
`_dispatch` 闭包取值这些点没有问题，同时**找出两个真实缺陷**——两个都会
在真实场景里生效，且我自己写的测试没能覆盖到。

### 缺陷 1（严重）：R5 的重建机制会死在它自己要救的场景里

`app/stages.py` 缓存 leaf 分片的一致性检查里，`cached.source_hash != source_hash`
被无差别当作**权威漂移**并 `raise StageError([BLUEPRINT_SPLIT_MANIFEST_AUTHORITY])`。
而语义重建**刻意**给受影响分片注入 `downstream_semantic_conflicts`，
正是为了改变 `source_hash`。第一轮蓝图本身是成功的 ⇒ 它的 leaf 一定已被
持久化为 `validated` ⇒ 第二轮必然命中这条 raise。

也就是说：**这个新机制在它设计要解决的那个场景下 100% 崩溃**，
而且崩在「重新生成蓝图」这一步本身（不在我加的 try 覆盖范围内），
用户既拿不到原始的语义门禁诊断，也拿不到修复结果。

我原有的 11 个用例全部 mock 掉了 `_generate_screenplay_narrative_blueprint`，
因此完全没有覆盖这条真实的 leaf 缓存交互路径。

**修复**：抽出 `_cached_leaf_superseded_by_feedback()` —— 只有当**本次激活确实给
这个分片注入了证据**且哈希因此变化时，才把旧 leaf 视为「不适用」（缓存未命中，
重新生成）；没有注入证据的分片仍走原来的严格漂移判定，严格性一个字未放松。
回归：`tests/test_blueprint_semantic_rebuild.py` 新增 1 例，覆盖三种组合。

### 缺陷 2（中等）：工具调用回退到 JSON 协议时思考预留被叠加两次

`chat_with_tools` 已经用 `text_request_token_limits` 换算过一次，
却把**换算后**的值传给 `_chat_tools_via_json_protocol`，
其非流式分支又调用 `chat()`——`chat()` 把它当作「答案预算」再叠加一次预留。
实测 `max_tokens=2000` 最终发出 `2000 + 2×16384 = 34768`，而不是应有的 18384；
在小上限模型上会直接顶满 `max_output_tokens`，与请求预算脱钩，
并可能重新引发仓库其它注释明确想避免的「max_tokens 过大触发 TPM 限流」。

另外流式分支走 `_stream_plain_chat`，它**完全不换算**，等于没有预留。

**修复**：`chat_with_tools` 把**原始答案预算**传给 JSON 协议回退路径；
流式分支在自己那一层换算一次。三条路径（原生 tools / 非流式回退 / 流式回退）
现在各自恰好换算一次。
回归：`tests/test_reasoning_token_budget.py` 新增 2 例，
已验证两例在修复前都会失败（2000 → 34768 / 流式分支完全无预留）。

#### 缺陷 C1（严重）：把一个**读可变状态**的门禁记进了缓存

我给 `screenplay_from_artifact_record` 加缓存时，把
`_assert_screenplay_artifact_contract` 挪到了缓存命中判断**之后**，

的纯函数。**这个断言是错的**，它读两处可变状态：

| 分支 | 读什么 | 为什么可变 |
|---|---|---|
| `plan is None` | `_historical_screenplay_artifact_is_bound` 查 `production_revisions` / `completion_certificates` / `episodes` / `evaluations` / `lineage` | 同一份不可变内容，「是否已被绑定」随 rebase / 续跑 / 重新发布而改变 |

#### 缺陷 C2（中等）：未命中路径把 artifact content 的嵌套对象直接交了出去


剧本模型上所有这类位置都在 `narrative_plan` 里

#### 缺陷 C3（中等）：只读作用域会掩盖发生在它内部的写

`resolve_current_screenplay_authority` →
`assert_screenplay_matches_validated_v7_source` 会 fail-closed 地
`UPDATE artifacts SET status='stale'` 并 commit——**这个写发生在作用域内部**。

* 只读请求：计数不动，缓存 100% 生效；

##### 根因 R8-1 —— 门禁数的是**渲染片段**，不是**话轮**

DC3 的相邻 turn 里，多条共享**同一 speaker、同一 `source_text`**，
只是 `line` 是原句的连续片段：

```
turn[1].line = 师弟既然拿起了这面镜子，说明你与它有缘，这镜子有不少传说，尤其是它的神秘，
turn[2].line = 据说能获得此物，除大机缘外更需要大造化，想必师弟就是具备这种气质之人，
两者 source_text 相同 = 完整那一句
```

来源查明（`app/screenplay_ir.py:5266`）：

```python
spoken_parts = _split_spoken_line(unit.text, max_chars=config.MAX_SPOKEN_CHARS_PER_SHOT)
if len(spoken_parts) > 1:
    compiler_audit.append({"operation": "split_by_spoken_capacity",
                           "reason": "downstream_single_shot_voice_capacity"})
for part_index, line in enumerate(spoken_parts):
    dialogue_chain_rows[chain_key].append(KeyDialogueTurn(...))
```

也就是说：**一句台词被按「单镜头配音容量」有意切成多段**，
这在渲染层是对的；但每一段都被登记成一个 `KeyDialogueTurn`，
而 `DIALOGUE_CHAIN_LENGTH_INVALID` 数的是「1~8 个连续**话轮**」——
话轮是语义概念（谁说了一次话），片段是渲染概念。**度量单位错了。**

**这不是偶发个案**（全库统计）：

| 指标 | 数值 |
|---|---:|
| 库内 dialogue_chain 总数 | 233 |
| **含被切碎 turn 的 chain** | **52（22.3%）** |
| 其中最长片段 run = 2 / 3 / 4 | 32 / 18 / 2 |
| 超过 8 轮上限的 | 2（均在 EP4） |
| **按 (speaker, source_text) 合并后仍超限的** | **0** |

合并是**可证明无损的**：两条失败 chain 的每一组片段，
`"".join(片段 line) == source_text` **逐字相等**（已验证全部 9 组）。
DC3: 11 → 5 轮，DC5: 9 → 4 轮。

##### 根因 R8-2 —— 上限只在**一个生产者**里执行，其余写 chain 的路径都不受约束

`DIALOGUE_CHAIN_TURNS_HARD_MAX = 8`（`app/renderability.py:20`）只有
`app/screenplay_ir.py:5405` 的分块循环真正执行：

```python
for offset in range(0, len(turns), DIALOGUE_CHAIN_TURNS_HARD_MAX):
```

而**所有其它写 `chain.turns` 的地方都不检查它**：

| 位置 | 行为 | 是否守 ≤8 |
|---|---|---|
| `screenplay_ir.py:5428` | 分块产出 | ✅ 唯一执行者 |
| `validators.py:1656` | `normalize_…` 按场次拆分 chain | ❌ |
| `validators.py:1696` | `normalize_…` 合并相邻 chain | ⚠️ 只在合并时判 |
| `validators.py:1472/1549` | 归一化 turn 列表 | ❌ |
| `screenplay_repair.py:5028` | `dialogue_chain_continuity` 补话轮 | ⚠️ 只在自己加时判 |
| `screenplay_repair.py:1119` | 归一化 | ❌ |
| `screenplay_document.py:1450` | `_chains_from_scene_turns` 回退重建 | ❌ |
| `portraits.py:6325` | | ❌ |

实测确证：把 chain 摆成 IR 分块器的口径 `[1,1,8,7,8,3,…]` 再跑
`normalize_screenplay_dialogue_chains`，输出**原样不动**；
把存下来的 `[1,1,11,4,9,2,…]` 再跑一遍，同样**原样不动（幂等）**。
即：**共享归一化器完全不认识这条上限**，11 轮的 chain 一路畅通到硬门禁才被拒。

##### 根因 R8-3 —— 分块边界会切在**一句话中间**

```
DC3 末轮 speaker=宝阁精明男子 source_text=师弟，拿起就是有缘，岂能因它看似凡俗就放弃？…
DC4 首轮 speaker=宝阁精明男子 source_text=师弟，拿起就是有缘，岂能因它看似凡俗就放弃？…
        -> 同一句被切到两个 chain：True（DC5/DC6 同样）
```

按片段数切分，边界必然可能落在一次发言内部，把半句话分给下一组。

##### 为什么修复层拿不出补丁（0 个）

`screenplay_repair` 里与 chain 长度相关的策略只有
`dialogue_chain_continuity`，它的作用是**往 chain 里补漏掉的话轮**
（`if len(turns) >= DIALOGUE_CHAIN_TURNS_HARD_MAX: continue`），
**没有任何策略能让一条过长的 chain 变短**。
这与 R6 是同一形状：**规则被放在唯一修不好它的那一层**。

##### 与 R5 的关系（别搞混）

一开始我怀疑是 R5 那个「按逗号切分源单元」的老根因，
查证后**不是**：这里的切分是 `_split_spoken_line` 按配音容量做的
**有意**切分，`compiler_audit` 里有显式记录。
两者相似之处只在于「一个层的合理切分被另一个层当成语义单位来数」。

##### R8 的系统性修复：把上限从「某个生产者记得做」改成「共享归一化器保证」，并按发言切分

**先否掉一个看似显然的方案**：把片段合并回整句。**不能这么做**——

```python
# app/validators.py:1801（既有硬门禁）
if content_char_count(line) > config.MAX_SPOKEN_CHARS_PER_SHOT:   # 36 字
    errors.append("[DIALOGUE_TURN_CAPACITY_EXCEEDED] … 必须按原文标点拆成同说话人的连续话轮")
```

即：**长句必须切碎**是另一条硬门禁的明文要求。合并会立刻违反它。
两条门禁对「单场景里的长对话」**联合不可满足**——这才是 R8 的本质，
与 R5 同属「合同本身无解」那一类。所以只能**多切几条 chain**，不能少切话轮。

**修复 1（`app/renderability.py`）**：新增共享判据

```python
def dialogue_turn_speech_acts(turns)          # 连续同 speaker + 同 source_text = 一次发言
def chunk_dialogue_turns(turns, *, limit=8)   # 按发言装箱，绝不切进一次发言内部
```

`source_text` 为空时不合并（无法证明同源，保守）。
单次发言本身就超上限时退化为硬切并终止——保证长度上限（硬门禁会拒稿）
优先于保证发言完整。放在 `renderability.py`：常量本来就在这里，
`screenplay_ir` 与 `validators` 都已依赖它，不引入新的循环依赖。

**修复 2（`app/screenplay_ir.py:5405`）**：分块循环改用 `chunk_dialogue_turns`，
不再按片段数硬切，边界不会再落进一次发言内部。

**修复 3（`app/validators.py`，R8-2 的核心）**：
在共享归一化器 `normalize_screenplay_dialogue_chains` 末尾兜底执行上限。
这样无论 chain 由哪条路径产生或改写（7 处不设防的写入点），
都不可能把违规 chain 交给硬门禁。

##### 为什么「拆分」而不是「合并」在下游是零影响的

`derive_key_lines` 是按 chain 顺序**展平**话轮再按正文重排
（`app/validators.py:1298`）。拆分只增加 chain 边界，
**话轮的顺序与数量都不变** → `key_lines` 与 `KL##` 编号逐字不变 →
已生成分镜里的 `shot.key_line_ids` 不会错位。
合并则会改写 key_lines 并让全部 KL 编号从合并点起整体位移。
