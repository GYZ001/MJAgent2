# AI 产品力前沿扫描报告与实施方案

> 2026-09-23 · 基于 main@7b211e52 · 只读扫描，未改动任何代码、未调用任何模型或视频供应商

## 0. 结论先行

**三个问题的直接回答**

1. **manager agent 可以做，但要做成「控制面上的制片主管」，不做「角色扮演团队」，也不接管工作流。**
   - **业界现状**：2026 年业界的共识是，写操作保持单线程，其余 agent 只贡献判断、不直接动手（Cognition 2026-04）。多智能体只在三种情形划算：上下文隔离、并行探索、专业化（Anthropic 2026-01）。
   - **本仓实测**：09-02 的 14 类故障里，0 条根因是缺上下文；5 条是代码拒绝了模型的正确输出，4 条是代码/并发问题，4 条是提示词契约缺口。瓶颈不在「思考者不够多」。
   - **制片主管补的是现在没人做的那一环**：各级自愈机制升级出来的问题、跨阶段问题，以及「要不要再花视频额度」的决策，今天全靠人守着页面。
   - **做法**：它只取证、只提建议，写入仍走命令总线，由人批准。
2. **harness 还能优化，而且优先级高于增加 agent 自主性。** 最值得修的是四处证据链断点：
   - 上下文清单和实际发出的载荷是两套东西，且只覆盖 3 个阶段。「模型有没有收到标准答案」至今要靠人工翻原始请求。
   - 响应 schema 与业务校验靠人工对齐。9 月以来按提交说明粗分，约 19 条（宽口径 43 条）提交在修这类不对齐。
   - 至少有四套各自计预算的循环、两份退避重放实现（外加一处没有重放），以及五层并发闸门。
   - 案头助手绕过 model_gateway 直连供应商，回合与审批状态只存在内存里。
3. **最大的产品力杠杆不在视频侧，而在免费的文本侧和人工信号上。**
   - **现状**：文本调用免费、视频按额度计费，但缺陷今天主要靠真人看成片发现。9 月的 433 次提交里有 239 次是修复，10 次带「第 N 轮」实测标记。
   - **方向**：把发现问题的环节前移到「金样评测 + 已标定的二值检查 + 合规预检」；把散在各台的「出路」收拢到一个收件箱。这是投入产出比最高的方向。

### 2.3 状态、恢复与幂等：本仓最扎实的部分

- **任务领取**：CAS 领取，租约 120 秒可续；失去租约即抛 `LeaseLost`（app/orchestration/media_scheduler.py:123-170、app/media_exec/checkpoints.py）。
- **视频提交防重复**：
  - 先用 CAS 写入 `provider_operation_id` 和 `submitting` 状态，再发请求，请求带 `Idempotency-Key`。
  - 同一个幂等键如果请求体变了，直接拒绝。
  - 重启后，处于 submitting/unknown 的任务进入 waiting_provider，不会重新提交。
  - 证据：app/media_exec/run_job.py:423-432、app/seedance.py:93-108、app/media_exec/worker_loop.py:124-128。
- **视频额度**：按尝试预扣，没有产出成功版本就退还（app/quota.py:427、486、523）。
- **开机恢复**：`recover_all` 覆盖从人物谱到交付的十余个阶段（app/recovery.py:164-194）。
- **命令总线**：约 76 个命令，风险分级 R0–R3，审批 token 绑定参数哈希（app/capabilities/policy.py:80-92）。

业界 durable execution（Temporal / DBOS / Inngest）的核心模式是步骤日志、幂等键、从最后完成的步骤恢复。本仓在媒体和流水线侧已经基本具备，而且没有引入外部服务。唯一的缺口在 agent 侧：助手的循环状态和审批 token 只存在内存里（app/agent/orchestrator.py:60-62、app/agent/approvals.py），重启后只能给出终态。

### 2.4 质检与反馈回路：最大的缺口

- **视频只做技术校验**（文件、容器、时长）。
  - VLM 打分质检 08-29 整体退场，理由是「评分可靠性为 0」（docs/STORYBOARD_PROMPT_IR_DESIGN.md:208-219）。
  - 唯一在用的视觉模型是字幕闸门（app/media_exec/subtitle_gate.py:1-20）：只问一个二值问题，经过标定（4/4 判对），原话留档，模型调用失败就放行。
  - **这是本仓已经验证过的「视觉模型该怎么用」的范式。**
- **采纳首个技术有效的候选**，不在多个候选之间择优（app/video_supervisor/adoption.py）。在视频计费的前提下，这个取舍是对的。
- **没有生成前的合规预检**。实例：「那根越来越粗了」被供应商以 `InputTextSensitiveContentDetected` 连续三次拒收，最后靠人工改台词解决（app/production/storyboard_dialogue_revision.py:1-6）。
- **人工信号只在当次生效，不沉淀**。
  - 台词修订的原句 `revised_from`、采纳理由、人工改写的提示词指令、客户评分都已落库，但只服务当次的业务判定和交付导出，没有进入任何评测或规则改进的回路。
  - 被拒素材会被永久删除（app/rejected_media.py:1）。
- **评测资产已过期**。
  - golden/ 只有一个旧契约的斗破第 1 集可渲染性基线。它读的是旧的 shots 结构，与分镜台 2.4.x 不兼容。
  - app/evaluations/ 只做问题码解析。
  - PROMPT_SPEC 里写的「三本小说金样回归」没有落地。

### 2.5 产品形态

- **页面**：侧栏有世界书（4 个子页）、映射台、分镜台、生成台、成片台、连播台，另有 7 个系统页（frontend/src/appSections.ts:72-131）。手动做一集大约要点 7-10 次；连播台可以一键跑完映射→分镜→确认→生成→成片。

- **对话入口已移除**：案头助手前端 08-22 应你要求删除（72412ce1）。后端仍在维护，现在只通过 MCP/API 对外。
- **一处界面承诺与行为不一致**：
  - 行为：连播流程由系统以 `decided_by="series_film"` 代签分镜确认（app/domain/series_ops/stages.py:139-154）。

**3.1 多智能体与 manager 模式。**
- **外部证据**：
  - Anthropic 的多智能体研究系统比单 agent 效果高 90.2%，但 token 消耗约为普通对话的 15 倍，且 token 用量本身就解释了 80% 的效果差异[1]。
  - Anthropic 2026-01 的指南把适用情形收窄为三种：上下文保护、并行探索、专业化。原话是「此外，协调成本通常超过收益」；多智能体实现通常多耗 3–10 倍 token[2]。
  - Cognition 2025 年的反面论证用 Flappy Bird 的例子说明：并行子 agent 缺少共享上下文时，会各画各的风格[3]。
  - Cognition 2026-04 的更新给出当前有效的形态：「写操作保持单线程，额外的 agent 贡献智能而非动作」；并点名「并行写者群」和「无结构的 agent 协商网络」无效[4]。
- **映射到本产品**：
  - 分镜与剧本是强耦合写作（跨段去重、台词账本、时段备忘），正是并行写者会出事的地方。
  - 失败分诊、原文保真审查、额度决策属于「贡献智能」的活，适合交给一个有界的 manager。详见第 4 节。

**3.2 Ambient agent 与收件箱。**
- **外部证据**：LangChain 提出 agent 由事件触发，而不是等人发问[8]。与人的交互只有三种：
  - 告知（notify）：无需行动；
  - 提问（question）：卡住时问人；
  - 审批（review）：执行前请人批准。
- **本产品现状**：连播台已经是事件驱动的长任务，缺的是后两种交互的统一落点。今天「需要人做什么」散在各台的文案里，「出路走不到」一周连修 5 次就是症状。

**3.3 上下文工程。**
- **外部证据**：Anthropic 把上下文当作有限资源来管理[5]，并主张工具要为 agent 设计，返回有意义的上下文，而不是原始数据转储[6]。具体手段有三：
  - 按需检索：只带标识，运行时再取；
  - 结构化笔记；
  - 子 agent 隔离：只回传压缩后的结论。
- **本产品现状**：CLAUDE.md 已经总结出同一条教训，「模型答不出来时，先查它有没有收到标准答案」，但这件事还没有自动化：清单与载荷是两套，查一次要人工翻原始请求。

**3.4 评测驱动与评审标定。**
- **外部证据**：
  - 评审模型要当分类器对待：先有人工金标，再切分数据，报告真阳性率/真阴性率而不是准确率，并且定期复标[9]。
  - 未经针对性评测验证的「通用提示词改进」可能让子任务骤降。实例：某 RAG 引用合规子任务从 26/30 掉到 9/30[10]。
- **本产品现状**：字幕闸门的标定做法（已知阳性 + 阴性帧，4/4 判对）其实就是这套方法的微缩版。缺的是把它推广成常设的评测资产。

**3.5 生成-验证不对称。**
- **外部证据**：
  - 验证比生成便宜的任务，可以靠「多采样 + 验证」换取质量[12]。
  - 视频领域有「先在图像上生成-选择，再驱动视频」的做法：I4VGen 在 VBench 主体一致性上提升 8.06 个百分点[13]。
- **本产品的取舍**：
  - 成本结构是文本免费、视频计费，所以「多花算力」应当全部花在文本侧：合规预检、归属判定、原文保真审查。
  - 视频侧的多候选择优（例如 AniMaker 用 MCTS 在片段候选间搜索[16]）每个候选都要烧额度，不适合。

**3.6 学术流水线对标。**
- **同构性**：FilmAgent、MovieAgent、AniMaker 等工作与本产品同构，都是「剧本 → 角色库锚定 → 分镜 → 镜头生成 → 质检 → 合成」[14][15][16]。
- **本仓领先之处**：工程可靠性（租约、幂等、恢复、闸门）远超这些原型。
- **差距**：在自动质检与评测。VBench-2.0 用 VLM/LLM 加专用检测器的混合方式做细项判定[17]，思路与字幕闸门一致：拆成可标定的小问题，而不是给一个总分。

**3.7 提示词自动优化。**
- **外部证据**：GEPA 用自然语言反思代替标量奖励来进化提示词。论文自报平均超出 GRPO 约 10%，所需 rollout 最多少 35 倍[11]。
- **前提**：必须有评测集当裁判。在 P0-1 落地之前做这件事，等于让模型去迎合一个没人验证过的目标。

**3.8 MCP 新进展。**
- **外部动态**：2026-07-28 版规范把核心协议改为无状态，异步 Tasks 降为扩展；MCP Apps 规范化了服务端返回可交互界面的方式[20][21]。
- **判断**：本产品单租户，没有与外部 agent 互通的需求，暂不跟进。

## 4. Manager agent 专章：制片主管

### 4.1 定位

```
连播任务 / 各台状态转移
        │ 事件：阶段失败、WAITING_HUMAN、L5 升级、合规拒收、额度将尽
        ▼
  ┌──────────────────────┐   只读工具：查原文、查台账、查调用记录、查同类历史、估额度
  │ 制片主管（有界循环）  │ ◀──────────────────────────────────────────────
  └──────────────────────┘
        │ 提案：诊断 + 证据 + 推荐动作（命令 + 参数 + 预估额度）
        ▼
   收件箱卡片 ──人批准──▶ 命令总线（风险分级、参数哈希审批）──▶ 确定性工作流
```

一句话：**判断的活交给制片主管，写入仍归工作流与命令总线。** 它不直接写库、不生成内容，也不改提示词。

### 4.2 与现有自愈机制的分工

| 层 | 负责 | 本方案是否改动 |
|---|---|---|
| model_gateway | 传输级重试、换路 | 不动 |
| AgentLoop / 分镜 Supervisor / repair_router | 阶段内的已知修复梯 | 不动 |
| 视频 Supervisor | 镜头级重提 | 不动 |
| **制片主管（新）** | 上面各层升级出来的问题（L5、WAITING_HUMAN、连播失败）、跨阶段/跨集问题、是否再花视频额度 | 新增 |
| 人 | 回答提问、批准审批 | 经收件箱 |

### 4.3 工具、预算与输出契约

- **只读工具**（沿用身份调查工具的形态）：
  - 原文检索（返回逐字引文）；
  - 世界书与台词账本查询；
  - 运行时间线（workflow_runs / step_runs / run_events）；
  - 单次模型调用的请求摘要与上下文清单（依赖 P0-2）；
  - 错误日志与 qa_json；
  - 同类历史卡片及其最终处理；
  - 动作的视频秒数预估。
- **动作集**：只能从能力目录（约 76 个命令）里选；执行一律经命令总线与参数哈希审批。
- **预算**：
  - 每张卡最多 6 轮 × 每轮最多 3 次工具调用；同一错误连续 2 次即停。
  - 所有模型调用走 model_gateway，顺带修掉助手直连供应商的旁路。
- **输出契约**：
  - 诊断：一句话。
  - 证据：逐字引文、provider_call id、错误 id，校验时逐条回查是否存在。
  - 推荐动作：命令名与参数，参数先过该命令自己的 schema。
  - 另附预估额度和不确定性说明。
- **校验失败时**：证据回查不上或命令不存在，整条提案丢弃，不做兜底，卡片以「未诊断」原样呈现。查不清就写查不清。

### 4.4 分三阶段放权

| 阶段 | 放权范围 | 启用条件 |
|---|---|---|
| A | 只诊断、只提案，一律由人执行 | 默认 |
| B | 自动执行「R0/R1、视频额度为 0、可撤销」的动作（例如重跑某集的文本阶段、刷新检查点）；每次写审计并在卡上留痕 | 需你开启 |
| C（额度管家） | 连播任务设视频额度预算；任何新视频提交（重提、重跑、补齐）超出余量时，改为生成审批卡，而不是直接提交 | 需你开启 |

### 4.5 为什么不做「导演 / 编剧 / 摄影」多 agent 团队

1. **写作强耦合**：分镜与剧本并行写会产生风格和事实冲突[3][4]。本仓为跨段一致性专门建了台词账本、时段备忘和跨段去重，拆给多个写者就等于拆掉这些机制。
2. **瓶颈不在数量**：09-02 实测 14 类故障，0 条源于缺上下文，瓶颈不在「思考者不够多」。
3. **墙钟约束**：文本虽然免费，但延迟和文本并发槽位是真实约束。多智能体 3–10 倍的调用量会直接变成墙钟时间[2]。
4. **可调试性**：本仓的调试方法论依赖「一次调用、一份载荷、一个判据」。

可以并行的是只读子任务：整集原文保真审查（按段并行、只读、回传压缩结论）和多集失败批量分诊。这正是[2]说的「上下文保护 + 并行探索」情形。

### 4.6 怎么判断它有没有用

- **一致率**：推荐动作与人最终处理的一致率。用历史 WAITING_HUMAN 记录回放评测，起步只展示、不执行。
- **效率**：阻断从出现到解除的中位时长，以及每集人工介入次数。
- **底线**：额度越权次数必须为 0。

### 6.2 各项细则

#### P0-1 分镜台 2.x 金样评测集 + 人工信号回收（M）

- **目标**：把「真人跑整集才发现问题」前移为「改提示词/规则之前先跑金样」。只跑文本阶段，不花视频额度。
- **做法**：
  1. **建金样**：从已人工核查过的项目（《我欲封天》、《龙猫出爪》剧本体、斗破）中抽 6 集起步。
     - 标注内容：台词账本（每句的说话人与原文出处）、登场角色、场景归属（按机位判定）、时段。
     - 标注方式：由子代理根据已核查的产物和人工修订记录起草，你来抽检。
  2. **确定性指标**（不需要评审模型）：
     - 台词保留率、说话人正确率、跨段重复台词数；
     - 原文单元的覆盖与重复、引用合法率；
     - 时段备忘错误率、场景归属正确率、登场角色建卡率。
  3. **运行器**：
     - 在生产快照的沙箱副本上，只调用文本阶段的入口。
     - 运行结束后断言：沙箱里视频任务表零新增。
     - 每个配置跑 3 次看分布，不以单次结果定输赢。
  4. **回收人工信号**：
     - 以下三类自动登记为评测用例候选：台词修订、越过质量判定的人工采纳、合规拒收后的改写。
     - 被拒素材改为保留元数据和少量抽帧（需你拍板，见 6.4）。
- **落点**：
  - 扩展已有的 app/evaluations/ 包；
  - 金样放在 golden/v2/；
  - 运行器放在 scripts/ 下。
  - 新模块在 LAYERS.toml 中声明层号。
- **验收**（挂在产物信号上）：
  1. 对当前 main 产出基线报告。
  2. 在沙箱里手写一份 b79e4214 修复前的函数副本，指标必须能抓到这次退化。这样红绿验证有独立的观察点。

#### P0-2 上下文清单即载荷 + 调用前必备上下文断言（M）

- **做法**：
  1. **清单来自实际载荷**：由 ContextPack 负责渲染最终发送的上下文块，调用方不再另外拼字符串。清单（键、字节数、哈希、来源产物、截断方式）从渲染结果推导，随 provider_calls 一起落库。
  2. **必备上下文断言**：
     - 每个契约声明「本次输入中出现的实体必须携带哪些上下文」。例如：本段每个出场身份必须带外观块，每句预留台词必须出现在载荷里。
     - 判据从本次输入推导，不维护名单。
     - 缺失即 fail closed，并报出具体缺了什么。
  3. **迁移顺序**：按事故密度，依次为分镜 → 映射 → 剧本 → 其余阶段。
- **落点**：app/harness/context.py 及各阶段的调用点。
- **验收**：
  1. 清单逐块的哈希与 provider_calls 中的原始请求一致。这里用第二条独立的读取路径核对。
  2. 手写一份「丢掉外观块」的修复前副本，必须在调用之前被拦下。

#### P0-3 契约两侧边界实例对齐测试（S–M）

- **做法**：
  1. **发现调用点**：用 AST 扫描自动找出所有结构化调用点。扫不到就先报红，不维护清单。
  2. **构造并校验边界实例**：
     - 用金样或 provider_calls 中的真实输入，构造出当次实际发送的动态 schema。
     - 枚举边界实例：每个 enum 值（含 `""`）、可选字段缺省、数组长度取 0 / 1 / 上限、字符串长度边界。
     - 把这些实例喂给业务校验。schema 合法而校验拒绝，测试就报红，并指出是哪个字段「宽的一侧」。
  3. **修法照 CLAUDE.md**：两选一：
     - 改成能表达条件的结构（带 tag 的联合）；
     - 写成提示词里的完整正面陈述。
     不放松校验，也不兜底。
  4. **扩大 strict 前先核实**：先确认 HiAgent 各路由是否支持 strict json_schema，再决定是否扩大强制范围。
- **约束**：生成器自研，规模小，不引入新依赖。
- **验收**：
  1. 用 ERR-20260831-45404d 修复前的契约（手写副本）跑，必须报红。
  2. 当前 main 跑出的「宽侧清单」逐条处理。

#### P1-1 统一收件箱（L）

- **收件箱是投影，不是第二份事实。**
  - **数据来源**：卡片从已有的权威状态推导，包括 WAITING_HUMAN、L5 升级、连播失败说明、合规拒收、字幕闸门拦截、额度不足。
  - **自建表只存**：已读、已处理、agent 批注。
  - **好处**：不给热路径事务增加写入，也不会出现「状态转了、卡片没建」的双写不一致。
- **卡片结构**：类型（告知 / 提问 / 审批）、对象（项目/集/段/镜）、结论、证据链接、后果（预估视频秒数、影响范围）、动作列表。
- **把出路做成数据**：
  - 提问卡和审批卡至少带一个可执行动作。动作 = 能力目录里的命令 + 参数 + 风险级，且当前用户有权执行。
  - 投影函数的单测断言：每种来源都至少产出 1 个可执行动作。
  - 这样「出路走不到」就从文案问题变成了一条会报红的测试。
- **推送**：用 SSE 推送角标和新卡片，轮询作为降级方案。
- **顺带修正**：连播自动确认与文档承诺的不一致（见 6.4 第 3 条）。
- **约束**：
  - 新建 app/inbox/ 包，存储层和接口层分别声明层号。
  - 建表走迁移，不用懒建表。09-11、09-12 两次因懒建表静默破坏了事务。
  - 前端单文件不超过 300 行。
- **验收**：从近 30 天的 error_logs 和 WAITING_HUMAN 记录中抽 20 个真实阻断场景，在沙箱里每个都能出卡，且至少有一个按钮能执行成功。

#### P1-2 制片主管 agent（L，先做阶段 A）

- **做法**：
  1. 按第 4 节实现阶段 A。
  2. 把助手和主管的模型调用改走网关。
  3. 审批与回合状态落表。
- **评测先行**：
  - 用历史 WAITING_HUMAN 卡片加上人最终的处理方式，作为主管的评测集。
  - 起步只展示、不执行。一致率的基线测出来之后，再讨论阶段 B。
- **验收**：
  1. 20 个历史阻断回放全部给出诊断，或明确给出「查不清」。
  2. 所有调用都能在 provider_calls 中查到。
  3. 零额度越权。

#### P1-3 视频提交前合规预检（S–M）

- **检查时机**：分镜确认之后、提交视频之前。
- **检查内容**：用免费的文本模型逐段检查 prompt_text 和台词，输出三项：
  - 风险原句：必须逐字命中本段文本，否则丢弃该条；
  - 风险类别；
  - 改写建议。
- **有风险时**：生成提问卡，展示原句和建议改写，并提供「接受改写」按钮。
  - 按钮直接走已有的台词人工修订入口，原句留在 revised_from。
  - 不自动改写：你 09-15 拍板过，措辞由人来改。
- **标定**：
  - 样本：历史上被供应商拒收的段落作阳性，已成功生成的段落作阴性。
  - 报告召回率和误报率。
  - 不达标就只作提示，不拦截。
- **收益**：拒收是否消耗额度取决于退还逻辑，这一点未逐条核实；但至少能省掉整集中断和人工来回沟通。

#### P1-4 已标定的二值视觉检查（M）

- **流程**：沿用字幕闸门的范式——抽帧 → 视觉模型回答一个二值问题 → 模型原话与命中帧留档 → 写入 qa_json → 在收件箱发告知卡。
- **首批两问**：
  1. 画面的昼夜是否与本段时段备忘一致（你的原话是「白天说着说着就变成黑夜」）；
  2. 画面人数是否与本段在场人物一致。
- **约束**：
  - 只留痕，不自动重提，因为重提要花额度。
  - 人工采纳仍是最高优先级。
  - 每个检查都要有标定报告（真阳性率/真阴性率），不达标不上线。
- **暂缓**：「是否同一角色」的比对放到 P2 探索。漫画风格下，人脸特征模型的可靠性未知，需要单独标定。

#### P2 摘要

- **P2-1 反思式提示词优化**：以金样为裁判。模型读失败样本，提出规则或提示词的修改；在金样上多次 A/B；生成 diff，由人审阅后合并。方言规则的分包与渐进式加载也在这一步一并考虑。
- **P2-2 循环内核收敛**：统一成一个有界循环原语，管住轮数、工具调用次数、停滞检测和指纹环检测；退避重放合并为一份。
- **P2-3 归属自洽投票**：说话人、场景归属独立采样 3 次，一致才采纳；有分歧就转调查工具或生成提问卡。**身份判定子阶段按契约禁止重采样（model_gateway.py:635-713），不适用。**
- **P2-4 录制回放**：从 provider_calls 按 operation_id 回放。
- **P2-5 上下文缓存**：先核实供应商是否支持。

### 6.3 顺序与依赖

```
第 1 批（并行，按文件所有权切分）：P0-1 ‖ P0-2 ‖ P0-3
第 2 批：P1-1 收件箱 → P1-3 合规预检（出卡依赖收件箱）
第 3 批：P1-2 制片主管阶段 A（依赖 P0-2 的清单、P1-1 的卡片、P0-1 的评测方法）→ P1-4
```

- **规模口径**：S ≈ 1–2 天，M ≈ 3–5 天，L ≈ 1–2 周（子代理实施 + 主会话验收），均为粗估。
- **文件属主**：P0-2 和 P0-3 都可能改到 model_gateway，派单时要指定唯一属主。
- **代码规范**：所有新代码严格满足文件与函数规范，不进基线。

### 6.4 需要你拍板的点（括号内为我的默认）

1. **制片主管能否自动执行动作**（默认只做到阶段 A；阶段 B 等你看过一致率再开）。
2. **被拒素材是否保留**（默认保留元数据 + 每条 3 张抽帧缩略图，保留 90 天，仅供内部评测。若有合规要求必须彻底删除，则只留元数据）。
3. **连播自动确认分镜与「分镜人工确认后才花钱」的承诺冲突**（默认改文档对齐现行为，并在建连播任务时明确提示「将自动确认分镜并开始消耗视频额度，预计 X 秒」）。
4. **金样规模**（默认 6 集起步，你抽检 20% 的标注）。

### 6.5 风险

| 风险 | 应对 |
|---|---|
| 金样过拟合 | 保留一组留出集，并定期纳入新小说 |
| 评审模型漂移 | 模型版本变更后必须复标定 |
| 收件箱沦为噪音 | 告知类默认聚合，只有提问和审批计入角标 |
| 主管误判 | 起步只读；每条提案带可回查的证据；与人工处理结果对账 |
| SQLite 写锁 | 收件箱是投影，不在热路径上增加写入；主管的诊断写入走独立短事务，不等锁 |

### 6.6 北极星指标（基线在 P0 阶段实测，不预设数字）

- 连播无人工介入出片率（按集统计）；
- 视频额度效率 = 提交的视频秒数 ÷ 交付成片秒数；
- 每集人工介入次数、阻断解除的中位时长；
- 金样指标：台词保留率、说话人正确率、跨段重复台词数、时段错误数；
- 真人跑片新发现的缺陷数：应当下降，且更多缺陷在金样阶段就被抓到。
