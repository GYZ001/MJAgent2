# 监制房功能体验扫描与优化建议

> 扫描日期：2026-07-26  
> 扫描角色：首次接触系统、需要追踪制作进度并处理异常的监制/制作负责人  
> 扫描环境：本地前端 `http://127.0.0.1:5230/monitor`，后端 `http://127.0.0.1:8230`，桌面视口 1280×720  
> 评分口径：10 分为优秀；7 分为基本顺畅；5 分为能用但需要学习或绕路；3 分及以下为容易误判、卡住或误操作

## 一、结论摘要

监制房当前的优势是“信息覆盖广”：运行、任务、模型、调用日志、并发和预算设置都已经集中到一个页面，搜索、筛选、分页等基础操作也能正常工作。

但它更像面向开发人员的观测控制台，而不是面向监制的异常处理工作台。用户可以看到很多状态和原始数据，却经常无法直接回答三个最关键的问题：

1. 现在真正卡在哪里？
2. 我下一步应该做什么？
3. 点击后能否直接到达需要处理的对象？

综合体验评分：**5.2 / 10**。

建议优先修复三类问题：

1. **避免错误的“系统正常”信号**：加载中或接口失败时，当前页面会用 `0`、`0/0`、“当前没有失败”等空状态代替加载/错误状态。
2. **补齐异常处理闭环**：任务失败、人工门禁、运行提醒虽然都有入口，但缺少重试、跳转、审批或带上下文定位。
3. **阻止无效配置进入数据库**：系统设置全部使用自由文本框，前端没有类型/范围校验，后端也只校验少数字段，容易造成“页面显示值”和“运行时实际生效值”不一致。

## 二、扫描范围与方法

本次按真实用户路径逐项体验了：

- 监制房入口和六个子菜单；
- 总览指标、异常列表、最近任务、配置概况；
- 运行列表、步骤时间线、审计事件、人工门禁和证据抽屉；
- 任务搜索、状态筛选、分页和恢复摘要；
- 模型分配、模型库、添加模型、配置连接和连接测试门槛；
- 调用日志搜索、状态筛选、分页和请求/响应/元信息展开；
- 系统设置编辑、脏数据判断和保存前状态；
- 页面右下角运行提醒的“查看详情”入口。

为避免影响正在执行的真实任务，本次没有执行取消任务、删除模型、保存系统设置、真实模型连接测试和任何可能产生费用的操作。相关写操作的风险同时通过实现代码进行了核对。

扫描时数据规模约为：运行/历史任务总计 361 条，任务页仅返回最近 200 条；模型 18 个，其中 4 个已配置连接；人工门禁 9 项；调用日志页返回最近 200 条。数据会随后台任务继续变化。

## 四、用户最可能觉得不好用的功能

### 1. 运行中心：看得到，但处理不了

这是最容易让监制产生挫败感的区域。

- 运行列表一次铺出 50 条，失败原因很长，缺少状态、项目、集数和时间筛选。
- `storyboard`、`episode_screenplay`、`step_xxx.iteration` 等内部名称直接暴露，用户需要自行翻译。
- “人工门禁队列”看起来像待办中心，但实际只有证据查看，没有“批准”“打回修改”“忽略并继续”或“去剧本台/分镜台处理”。
- 打开证据需要两次语义几乎相同的点击，第一次只是异步加载，第二次才真正打开抽屉。
- 证据详情中 JSON 解析片段、Artifact ID、Hash、Contract 和血缘适合排障，但没有把 blocker 先翻译成业务后果与建议动作。

优化方向：把运行中心改成“异常与待办优先”的工作台。默认只展示运行中、等待人工、失败和可恢复项；历史成功记录放到次级筛选。每个异常提供唯一主操作，例如“去剧本台修复”“从检查点恢复”“批准候选”“查看技术详情”。

### 2. 系统设置：最容易误操作并产生配置漂移

实际体验中，将“视频提交并发”从 `20` 输入为 `abc` 后：

- 页面没有任何即时错误；
- “保存系统设置”仍然可点击；
- 再改回 `20` 后，页面仍认为存在未保存修改。

实现上，前端只用 `draft` 是否含键判断是否修改；后端只对日志保留天数和少数模型路由做明确校验。并发读取层遇到非法整数会回退默认值，因此可能出现：

- 数据库和页面显示 `abc`；
- 运行时实际使用默认并发；
- 用户以为自己的配置已经生效。

此外，后端是逐项写入后再尝试热更新。热更新失败时会返回 warning，但前端无条件提示“系统设置已更新”，没有展示 warning，也没有把保存和运行时生效做成原子操作。

优化方向：为每个设置建立 schema，包括类型、最小值、最大值、步长、单位、默认值、是否实验、是否即时生效、依赖关系。前端使用数字框、开关和下拉框；后端在事务写入前完整验证整个 patch，热更新失败时回滚或明确显示“已保存但未生效”。

### 3. 调用日志详情：信息很多，但难以消费

展开一条分镜调用后，页面直接显示完整 system prompt、剧本、人物和场景数据、响应和元信息。单条记录可能长达数万字符，并包含本机绝对路径。

用户主要需要的是：调用目的、输入规模、模型、耗时、错误阶段、重试关系和下一步动作。完整原文应作为二级“技术详情”，默认折叠，并提供复制/下载。对本机路径、令牌形态字段和可能包含敏感内容的输入应默认遮罩。

### 4. 任务失败没有处理出口

任务队列的错误列已经能给出较好的中文解释，但表格没有：

- 查看详情；
- 重试/恢复；
- 取消；
- 跳到对应项目、集、镜；
- 复制错误码。

尤其某些错误文案明确写着“可点击重试”，但本页没有任何可点击的重试入口，会显著降低用户对产品文案的信任。

### 5. 运行提醒的“查看详情”不是真正的详情跳转

运行提醒仅调用 `go('monitor')`。它不传递 `run_id`，也不能指定运行中心子菜单。用户已经在监制房其他子页时，点击“查看详情”仍停留在原子页，没有可见反馈。

优化方向：支持 `/monitor?section=runs&run_id=run_xxx`，并让运行提醒、助手 Run 卡片、任务表和总览统一使用这条深链。

## 五、容易出现 Bug 的实现点

| 风险点 | 概率 | 影响 | 依据与表现 | 建议 |
|---|---|---|---|---|
| 加载/失败被伪装成空数据 | 高 | 高 | `MonitorPage` 只取 `usePoll` 的 `data`，没有使用 `loading` 和 `error`；`null` 被 `?? 0` 和空列表渲染成正常状态。首次进入已实际看到全 0，随后才变为真实数据 | 每个数据块显式区分 loading、error、stale、empty；保留最后成功值并显示更新时间 |
| 系统设置非法值落库、运行时回退 | 高 | 高 | 前端无类型校验；后端大多数字段直接 `str(value)` 后写库；并发层对非法整数静默回退默认值 | 共享设置 schema；事务前校验；返回并展示 `requested/effective`；禁止静默回退 |
| 系统设置部分写入 | 中 | 高 | 后端逐键 `set_setting`，后续字段校验或运行时热更新失败时没有整体回滚 | 用数据库事务先验证后写入；热更新失败时回滚或明确标记 pending_restart |
| 运行详情异步串线 | 中高 | 高 | 切换 Run 时，旧 Run 的 `/steps`、`/events` 请求没有取消标记；旧响应较晚返回时可能覆盖新 Run 详情 | 使用 AbortController、请求序号或 selected ID 校验后再 setState |
| 已选 Run 从最近 50 条中淘汰 | 中 | 中 | 列表轮询只保留 50 条，但 `selected` 不会在当前 ID 消失时自动切换；可能出现左侧无选中项、右侧仍请求旧记录 | 若 selected 不在新列表中，保留独立详情标题或自动选择首项并提示 |
| 人工门禁证据缓存过期 | 中 | 中 | `gateEvidence` 首次加载后一直缓存，不会随 5 秒门禁轮询刷新 | 记录版本/updated_at；门禁变化时失效缓存；抽屉提供手动刷新 |
| 总览数量与任务列表总数不一致 | 高 | 中高 | 总览对全部账本计数；接口把多类 recent 合并后硬截断 200，任务页显示“共 200 条”。本次总计 361 条，但页面只能访问最近 200 条 | 后端服务器分页与筛选；页面明确“最近 200 条”直到改造完成 |
| 总览指标下钻不带筛选 | 高 | 中 | 六个指标卡统一只执行 `openSection('jobs')`，不会按 queued/running/failed/paused 设置筛选；旧筛选还会被保留 | 每张卡传入明确筛选组，并清理冲突条件；标题显示筛选来源 |
| 运行提醒详情丢失上下文 | 高 | 中高 | `RunDock` 只调用监制房导航，未传 Run ID；监制房内点击无变化 | URL 化 section/run_id，并在 RunCenter 中选中目标 Run |
| 调用日志主线程卡顿 | 中高 | 中 | 超长 JSON 直接插入表格 DOM，无虚拟化、长度限制或懒加载 | 详情独立抽屉；摘要先行；大字段按需请求；使用虚拟滚动或文本窗口 |
| 状态枚举继续增长后出现英文 | 高 | 中 | 未进入 `CALL_STATUS_LABELS` 的新状态会被通用拆词，已经出现 `baseline / handoff`、`counter`、`needs / replan` | 后端输出稳定的 `status_category` 和 `display_label`；未知状态统一显示“内部事件”并保留技术码 |
| 页面功能回归缺少保护 | 高 | 中高 | 前端 23 个现有测试全部通过，但没有 `MonitorPage`、`RunCenter`、`RunDock` 的专门交互测试 | 补充组件测试和端到端测试，覆盖加载失败、深链、筛选、设置校验和异步切换 |

## 六、信息架构优化建议

建议把监制房从“六个平级技术模块”改为“监制任务优先、技术细节下沉”的两层结构。

### 默认层：今天需要处理什么

- 正在运行：当前步骤、已耗时、预计剩余时间、费用；
- 待我处理：人工门禁、预算暂停、修复失败、需要补充输入；
- 系统异常：供应商超时、网络故障、重试耗尽；
- 近期完成：可直接进入剧本台、分镜台、评审墙或成片台验收。

每个卡片只保留一个主操作和一个“技术详情”入口。

### 技术层：用于排障和配置

- 运行与步骤；
- 调用日志；
- 模型库与连接；
- 系统策略。

原始 JSON、内部状态码、调用者文件路径、Artifact 血缘应放在技术层，默认折叠。

## 七、分阶段优化路线

### P0：先消除误判和配置风险

1. 为 jobs、calls、settings、health、model catalog 增加加载、失败、过期状态，禁止用 0 代替未知。
2. 建立系统设置 schema；前后端统一校验类型、范围、枚举和依赖关系。
3. 设置保存改为事务；返回并展示运行时是否真正生效。
4. 修复无效脏状态：值等于服务端原值时从 draft 移除。
5. 修复运行提醒深链，确保“查看详情”选中对应 Run。

### P1：补齐异常处理闭环

1. 总览指标下钻时自动应用对应筛选，并显示来源。
2. 任务行增加“查看详情、去处理、重试/恢复、复制错误码”。
3. 人工门禁改成一次点击打开，增加批准、打回和跳转编辑页。
4. 运行中心增加项目、工作流、状态和时间筛选，默认隐藏成功历史。
5. 调用日志增加业务事件/模型请求分类、异常聚合和模型友好名称。

### P2：提升规模化与可维护性

1. jobs、calls、runs 改为服务端分页、搜索和筛选，返回 `total`。
2. 子菜单、筛选和选中对象进入 URL，支持刷新恢复、浏览器前进后退和分享。
3. RunCenter 请求增加取消/防串线，证据缓存增加版本失效。
4. 调用详情改为懒加载抽屉，增加摘要、遮罩、复制和下载。
5. 模型库增加搜索、服务商分组、能力筛选、仅看待配置。
6. 补齐无障碍：表格可展开行支持键盘、`aria-expanded`；重复按钮包含模型/任务名；弹窗支持焦点锁定和 Esc 关闭。

## 八、建议验收标准

- 后端不可用时，任何总览指标都不得显示为 0 或“没有异常”，必须显示错误和重试入口。
- 点击“已暂停 55”后，任务页必须显示已应用的暂停状态组，并能解释 55 的构成。
- 任意任务、运行提醒和助手 Run 卡片都能通过同一深链定位到具体 Run。
- `abc`、负数、超范围并发、非法布尔值和非法调度策略无法进入保存确认。
- 把设置改回原值后，“待保存”计数归零；离开页面前对真实未保存修改给出提醒。
- 后端设置更新要么全部成功并生效，要么全部不写入；不允许半成功。
- 任务页显示真实 `total`，不再把“最近 200 条”表述为全部记录。
- 调用日志默认不展开全文，不显示未遮罩的敏感字段和本机绝对路径。
- 人工门禁一次点击进入证据及决策界面，完成处理后队列数量立即更新。
- 新增至少以下自动化用例：加载失败、总览下钻、Run 深链、快速切换 Run、防止设置非法值、设置无变化、日志超长内容、键盘展开。
