# 人物谱与场景图功能体验扫描报告

> 扫描日期：2026-07-26  
> 扫描视角：首次完成小说导入、正在检查前期资产的普通制作用户  
> 扫描对象：前期准备中的「人物谱」与「场景库」  
> 测试样本：项目《斗破苍穹》，8 个角色、8 个场景，桌面端页面  

## 1. 结论先行

| 模块 | 综合体验分 | 结论 |
|---|---:|---|
| 前期准备导航 | 8.5 / 10 | 人物谱、场景库、分集规划的任务顺序清晰，入口容易理解。 |
| 人物谱 | 6.6 / 10 | 角色浏览、搜索、版本查看和参数查看较好用；定稿、付费重生、并发编辑和人物图 QA 可见性不足。 |
| 场景库 | 5.4 / 10 | 页面结构和详情弹窗已经可用，但核心质量门禁不可信，用户可能把错误场景当作合格资产投入下游。 |
| 前期资产整体 | 6.0 / 10 | “能操作”已经成立，“能放心采用”尚未成立。应先修质量门禁与付费防误触，再继续优化视觉细节。 |

最值得优先处理的四件事：

1. **场景图的“无人、无水印、多视角有区分”门禁没有守住。** 实测的「萧炎卧室」生成词明确要求无人、无水印，实际采用图却出现人物和右下角水印，仍显示“已采纳”和 QA 0.95。
2. **人物谱保存存在覆盖新数据的风险。** 后端已经支持 `expected_version` 冲突检测，但人物谱页面保存时没有传当前版本，长时间编辑期间若后台补入新角色，旧页面可能整份覆盖。
3. **付费生成缺少统一的费用预估和确认。** “重新生成当前造型包”“重新生成场景视角包”“检查并补齐场景图”“保存并重新出图”都可能直接进入付费流程，但只有单视角重做有明确确认。
4. **人物图 QA 对用户几乎不可见。** 场景图还能看到分数、问题和候选证据，人物图只有“已定妆”，用户无法判断三张视角的人脸、服装和发型是否真的一致。

## 2. 扫描方法与评分口径

本次采用三类证据：

- **桌面端实测**：实际进入人物谱和场景库，操作导航、搜索、横向切图、修订、影响确认、参数弹窗、候选图和证据抽屉。
- **样本资产目视检查**：检查卡片状态、生成词、图片内容、QA 分数、问题文本和多视角差异。
- **代码与测试核对**：检查前后端请求、版本控制、QA 阈值和异步任务实现；运行现有前后端测试。

为了避免实际扣费或改写项目数据，本次没有最终提交人物谱、重新生成素材或采纳新候选；这些写操作按界面分支、请求实现和后端门禁进行扫描。

评分含义：

| 分数 | 含义 |
|---:|---|
| 9~10 | 顺畅、明确，几乎不需要学习成本 |
| 7~8.9 | 可用，存在小摩擦但不妨碍完成任务 |
| 5~6.9 | 能完成，但容易犹豫、误解或返工 |
| 3~4.9 | 明显不好用，或有较高误操作/错误采用风险 |
| 0~2.9 | 核心流程不可用或结果不可信 |

## 6. 用户最可能觉得不好用的功能

### 6.1 定稿人物谱：知道影响很大，却不知道到底多大

影响弹窗会告诉用户下游可能失效，但精确数量写成“保存后计算”。用户真正关心的是：

- 会失效多少分集、分镜、参考图和视频；
- 哪些已经花过钱；
- 只改一个角色外观，与改全局画风的影响是否不同；
- 预计需要花多少钱恢复。

当前流程在确认之后才返回数量，属于“先同意，再知道代价”，体验分最低。

### 6.2 整包重新生成：按钮很轻，代价很重

人物和场景的整包重生都没有统一确认，而单视角重做反而会确认。用户很难建立稳定预期，也容易把“¥0.2/张”理解成整个角色或场景只花 ¥0.2。

建议所有付费入口共用一套确认卡：生成范围、图片数、单价、最大重试、预算上限、旧资产是否保留。

### 6.3 人物定妆：能看图，但无法做专业判断

用户可以左右切换三张人物图，却看不到：

- 人脸一致性、服装一致性、发型一致性分数；
- 哪个视角有具体问题；
- 是否有未采用候选；
- 为什么这个版本被自动采用。

对于人物一致性这个核心目标，仅有“已定妆”远远不够。

### 6.4 场景详情到候选/参数：操作后回不到原详情

从场景详情打开候选或生成参数时，详情弹窗先被关闭；完成后直接回场景列表。用户想继续查看同一场景的另一个信息，需要重新找到卡片并再次打开，形成反复进出的摩擦。

建议保留详情作为底层弹窗，候选和参数作为二级面板；关闭二级面板后回到原详情和原滚动位置。

### 6.5 长列表只支持名称搜索

当前样本只有 8 个角色和 8 个场景，问题不明显。长篇项目继续自动补角色和场景后，仅靠名称搜索会很难管理。至少需要：身份、首次出场、当前/历史、是否缺图、QA 状态、是否有候选、室内外等筛选与排序。

## 8. 优化路线图

### P0：先让“已采纳”值得相信

1. 将场景纯净度拆成不可被平均分抵消的硬门禁：无人物、无多余文字、水印政策一致、空间类型匹配。
2. 将多视角差异设为独立硬门禁：建立、对向、动作区必须可被分类器正确识别；相似度只用于预警，最终结合相机轴线和标志物方位判断。
3. 重新定义状态：
   - 绿色：已采用且所有硬门禁通过；
   - 黄色：已采用但有非阻塞警告；
   - 红色：硬门禁失败，不得作为生产参考；
   - 灰色：未验证或未出图。
4. 对现有场景库执行一次离线复验，自动找出“有人物、视角同构、场景语义错误”的历史资产。

### P1：降低覆盖、误扣费和长任务失败风险

1. 人物谱保存传 `expected_version`，发生冲突时提供差异合并。
2. 所有付费操作统一先预检，展示图片数、预计费用、最大重试预算、受影响资产和幂等键。
3. 单视角重做改为持久异步任务，支持进度、停止、断线恢复和历史尝试。
4. 人物谱补齐 QA 分数、问题、候选、证据和人工采纳，与场景库能力对齐。
5. 定稿人物谱前返回真实失效清单和重建成本，不再“保存后才知道”。

### P2：提升日常制作效率

1. 图片点击放大、1:1 查看、同角色/同场景多图并排和差异对比。
2. 列表增加筛选、排序、批量选择、页码记忆和滚动位置恢复。
3. 修订草稿自动保存、离开保护、修改对比和撤销。
4. 场景详情保留上下文，候选和参数作为二级面板。
5. 中文化所有用户状态；修复重复书名号、重复标点和重复画风串。
6. 补齐动作区视角说明，并根据实际存在的视角动态渲染指南。

## 9. 建议补充的自动化验收

| 验收项 | 建议标准 |
|---|---|
| 纯环境场景 | 任何可识别人物进入场景参考图时，候选不得通过硬门禁。 |
| 场景水印 | 生成政策与 QA 政策一致；若要求无水印，检测到水印不得显示绿色已通过。 |
| 对向视角 | 视角分类必须为 reverse angle，且标志物左右/前后关系与建立视角满足预期变化。 |
| 人物多视角 | 三个必需视角齐全，脸、发型、服装和体型一致，任一硬失败时整包不得切换。 |
| 并发保存 | 旧 `expected_version` 保存返回 409，页面提供刷新或合并，不覆盖新角色。 |
| 付费确认 | 所有会生成图片的入口都必须先显示图片数与费用上限，取消后无任务、无扣费。 |
| 长任务恢复 | 刷新页面或断开连接后，单视角重做仍能恢复进度并查看最终结果。 |
| 未保存保护 | 修改任一锚点后切换模块必须确认；选择留下后内容不丢失。 |
| 状态一致性 | UI 状态、QA 结论、证据状态和实际采用版本必须一致。 |
| 页面 E2E | 覆盖搜索/清空、详情、候选、证据、参数编辑、恢复默认、取消付费、版本冲突。 |

## 10. 现有测试结果与覆盖缺口

- 前端 TypeScript 类型检查：通过。
- 前端现有测试：7 个文件、23 项全部通过。
- 人物谱/场景相关后端定向测试：46 项全部通过。
- 浏览器控制台：本次操作期间未捕获前端 error/warn。

这说明当前代码在接口和既有回归层面较稳定，但现有测试主要验证“路由存在、任务和数据能流转”，没有覆盖以下产品语义：

- 场景明确要求无人时，图片中出现人物必须失败；
- 建立和对向视角必须真的不同；
- 高 QA 分不能掩盖硬问题；
- 人物谱页面必须携带版本号防止覆盖；
- 所有付费入口必须展示真实成本并确认；
- 人物多视角 QA 必须对用户可见。

因此，下一阶段应优先补“结果语义 E2E”和真实样本回归，而不是只增加接口单测。
