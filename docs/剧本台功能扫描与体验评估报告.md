# 剧本台功能扫描与体验评估报告

> 扫描日期：2026-07-26  
> 扫描对象：MJAgent2「剧本台」  
> 测试项目：《斗破苍穹》，1646 集  
> 测试方式：真实页面操作 + 窄屏检查 + 前后端代码核对 + 相关自动化测试

## 一、结论先行

剧本台已经具备一条完整的“选集 → 选必保留台词 → 生成/修复剧本 → 阅读与编辑 → 查看证据 → 进入分镜”工作链。阅读已交付剧本、搜索超长分集、查看证据和删除风险确认的完成度较好；真正拉低体验的是几个关键动作的语义和安全边界不够清楚。

- 功能项简单平均分：**6.4 / 10**。
- 按核心工作流和风险加权后的综合体验：**5.9 / 10**。
- 用户体感：**能用，但不够放心**。查看类功能普遍好用，编辑、恢复和进入分镜等高影响功能容易让用户担心误操作。
- 发布判断：建议先处理 2 个 P0 和 6 个 P1，再作为稳定生产工具推广。

最需要马上解决的两个问题：

1. **“进入分镜台”是导航文案，却会自动启动或续跑分镜任务。** 本次实测点击后，系统从已有 5 镜 checkpoint 自动续跑，最终保留 6 个 QA 通过镜头并再次失败。用户无法从按钮文案预判它会产生后台任务、等待时间和潜在费用。
2. **分镜生成中仍可进入手工编辑并点击保存。** 保存逻辑会清空下游，但后端保存路径没有先取消并等待正在运行的分镜任务，存在旧任务继续回写、刚清空的下游重新出现或新旧剧本产物混用的竞态风险。

## 二、评分口径与扫描边界

评分采用 10 分制：

- 9～10：清晰、稳定、几乎无需学习。
- 7～8.9：可顺畅完成，只有轻微摩擦。
- 5～6.9：能完成，但容易困惑、返工或误操作。
- 3～4.9：明显难用，或存在较高数据/状态风险。
- 0～2.9：核心路径不可用或不可接受。

验证标记：

- **实测**：在浏览器中实际点击、输入或切换并验证结果。
- **观察**：真实页面和真实数据可见，但没有提交付费或高影响动作。
- **代码核对**：通过前后端实现、状态判断和测试用例确认。

为避免不必要费用和数据破坏，本次没有批准“删除剧本”，没有提交“保存剧本”，也没有主动点击“首次生成整版”和“继续局部修复”。删除流程已打开服务端影响确认卡并点击“拒绝”，确认业务数据未被删除。

## 四、用户最可能觉得不好用的地方

### 1. “进入分镜台”不是纯导航

这是当前最容易造成负面体验的地方。用户看到“进入分镜台 →”，通常会理解为切换页面；实际实现会根据状态自动调用“首次生成分镜”或“从 checkpoint 续跑”，然后才导航。

本次扫描就是实际案例：点击前页面提示已保留前 5 个 QA 通过镜头；点击后自动进入修复运行，最终变为保留前 6 镜并再次失败。用户没有在点击前看到“将续跑分镜”“预计影响”“预计等待/费用”等信息。

建议拆成两个按钮：

- `查看分镜台`：永远只导航，不产生副作用。
- `继续生成分镜（从第 6 镜开始）`：明确动作、checkpoint、预计影响，通过服务端预检后执行。

### 2. 手工编辑像“把数据库 JSON 展开给用户”

编辑功能虽然字段齐全，但把主线、完整正文、场次、情绪、人物状态等全部堆在一页。用户要同时理解 20 多个字段，还要手写如下分隔格式：

- 主线节拍：`beat_id | who | does | turn`
- 场次结构：`场次标题 | 功能 | 摘要 | 冲突 | 转折 | 原文依据 | 角色`

任何正文中自然出现的 `|` 都可能让解析列错位；列数不足也会被静默补空。用户直到保存时才收到后端 422，而且错误只在短时 Toast 里展示，修改成本很高。

### 3. 状态多，但没有形成一句“现在该做什么”

页面同时展示剧本状态、分集状态、任务耗时、错误提示、能力边界和证据等级。信息不少，但存在互相打架的文案：

- 顶部“修复中”，下方“局部修复已暂停，可继续”。
- 顶部“已交付 + 待确认”，没有说明“待确认”的是分镜而非剧本。
- 修复暂停态的空页面仍写“点击首次生成整版”，实际入口却是“继续局部修复”。

用户需要自己推理状态机。建议顶部只保留一条主状态：`剧本已交付｜分镜修复暂停在第 6 镜`，紧跟唯一主操作。

### 4. 必保留台词没有“时长预算”

功能允许在 50 秒目标中全选 27 条台词，其中包含很长的段落。页面只提醒“剧本与后续分镜可能相应变长”，没有告诉用户：

- 预计口播多少秒；
- 超出目标时长多少；
- 哪些台词互相重复；
- 哪些台词应该成组保留；
- 当前选择是否会导致验证无法收敛。

这会把本可在提交前发现的问题推迟到数分钟的生成/修复后才暴露。

### 5. 手机端第一屏信息密度过高

390×844 下没有横向滚动，是优点；但剧本工具卡实测高约 670px。状态徽标、按钮、证据、计时、能力边界、4 个字段和错误提示全部在正文之前。用户打开页面后几乎看不到剧本，需要先滚过一整屏“系统信息”。

建议手机端只保留“主状态 + 主操作 + 更多”，其余信息折叠进底部抽屉。

## 五、最容易出现 Bug 的功能

| 优先级 | 风险点 | 触发条件 | 可能后果 | 依据 |
|---|---|---|---|---|
| P0 | 分镜运行中保存剧本的竞态 | `ep.status === scripting` 时进入手工编辑并保存 | 保存清空下游时，旧分镜任务仍继续回写；出现孤儿镜头、新旧剧本混用或状态回跳 | 保存按钮只受 `busy` 控制；后端保存路径删除镜头前没有 `cancel_and_wait(storyboard)` |
| P0 | 导航按钮隐式启动/续跑分镜 | 剧集为 `planned`、`script_failed` 或存在未完成 checkpoint | 用户无意启动长任务或费用；失败后误以为只是打开页面 | 本次真实点击已触发从 5 镜到 6 镜的续跑 |
| P1 | 陈旧草稿覆盖新版本 | 编辑期间 Agent、另一标签页或后台流程发布新剧本 | 旧草稿覆盖新版本，服务端已有 409 能力却不会被启用 | 后端支持 `expected_version`，前端保存请求未传 |
| P1 | 修复暂停态修改台词不生效 | 页面无可交付剧本、`canResumeRepair=true`，用户调整复选框后点继续 | 用户以为新约束会用于修复，实际 `/screenplay/resume` 请求体为空 | 本地 `selectedDialogueLines` 只用于首次 Baseline |
| P1 | 未保存编辑静默丢失 | 编辑后切集、点侧栏、浏览器后退或进入其他工作台 | 长篇修改全部丢失 | 页面无 dirty 标记、路由守卫或 `beforeunload` 提示 |
| P1 | 结构化字段被分隔符破坏 | 场次内容含 `|`，或用户漏填/多填列 | 字段错位并可能在保存后成为错误场次数据 | 前端用 `line.split('|')` 直接解析 |
| P1 | 双重确认导致误判和操作疲劳 | 保存剧本且已有分镜/媒体 | 先原生确认，再出现服务端“批准一次”；用户以为第一次已完成或误拒绝第二次 | 页面 `window.confirm` 与 Capability `WHEN_IMPACT` 同时存在 |
| P1 | 状态与空文案不一致 | 修复暂停且没有 published screenplay | 用户找不到文案所说的按钮，可能转而删除重来 | 空状态文案固定写“首次生成整版” |
| P2 | 重复台词无法按出现位置选择 | 原文两处出现完全相同台词 | 勾选/取消一处会影响同文本的另一处，无法表达语境 | 选择集合以台词字符串而不是 occurrence ID 为键 |
| P2 | 证据血缘失败被误认为“没有血缘” | lineage 请求失败 | 用户看到 0 个下游而非加载失败，错误决策 | 抽屉 `.catch(() => setLineage(null))`，无错误态 |
| P2 | 长任务轮询流量随项目规模放大 | 1646 集项目中任一剧集运行 | 页面持续请求项目 picker 和当前 episode；多标签页时放大服务端压力 | 本地实测 picker 125,158B/3s，script 35,710B/2s，合计约 3.6MB/分钟 |

补充说明：“原文来源范围”在编辑页显示为空，原因是前端使用空字符串而没有回退到章节范围。后端保存前会把空值补回 `第 N 章`，因此当前更偏向显示/信心问题，而不是最终数据丢失；仍建议修正，避免用户误以为必须手填。

## 六、优化方向

### P0：先把高影响动作做成安全状态机

1. 将“查看页面”和“执行任务”彻底分离，禁止任何导航按钮隐式启动任务。
2. 剧本保存前由后端原子执行：暂停/取消分镜任务 → 等待 worker 退出 → 校验当前版本 → 清空下游 → 写入新剧本。
3. 分镜运行中将手工编辑改为只读，或明确进入“创建草稿分支”；在任务结束前禁止发布保存。
4. 前端保存必须传 `expected_version: ep.screenplay_artifact_id`，409 时展示“当前版本 / 我的草稿”差异，不允许静默覆盖。
5. 高影响动作统一只保留服务端 Impact 批准卡，移除 `window.confirm`。

验收标准：

- 点击“查看分镜台”时网络中不得出现 POST。
- 任意运行态保存剧本时，旧任务必须先进入终态，且保存后 30 秒内不得再出现旧 run 的写入。
- 两个标签页并发编辑时，后保存的陈旧版本必须收到 409，不能覆盖。

### P1：把编辑器改成面向编剧的结构化工具

建议拆为 4 个页签或锚点：`主线`、`正文`、`场次`、`依据与状态`。

- 场次与主线节拍使用可增删的结构化行，不再让用户手写 `|`。
- 提供即时校验：必填、字符数、主线台词上限、台词是否真实出现在正文、目标时长估算。
- 提供脏数据标记、自动本地草稿、撤销/重做、离开前提示。
- 保存前展示差异摘要：改了哪些字段、会清空多少镜头/媒体、预计要重跑哪些阶段。
- 将“恢复拍摄”改成一个小向导：恢复原因 → 如何改成可见/可听内容 → 影响节拍 → 预览差异。

### P1：重做台词预算与修复语义

- 每条台词使用稳定 occurrence ID，不用文本字符串作为唯一键。
- 实时显示“已选 12 条 / 约 74 秒 / 目标 50 秒 / 超出 24 秒”。
- 对依赖上下文的问答、安慰、反驳自动成组；允许用户折叠查看原文上下文。
- 修复暂停态要么锁定台词选择，要么提供“保存新约束并重新规划修复”；不能显示可编辑但忽略修改。
- 标签“主线台词最多 6 条”应改成动态上限，解释必保留台词可能抬高上限。

### P1：统一状态和下一步文案

建立单一的展示状态选择器，例如：

| 实际状态 | 推荐主文案 | 推荐主操作 |
|---|---|---|
| pending | 尚未生成剧本 | 首次生成剧本 |
| running baseline | 正在生成首版剧本 | 停止生成 |
| repair paused | 局部修复已暂停 | 继续局部修复 |
| ready + storyboard empty | 剧本已交付，尚无分镜 | 生成分镜 |
| ready + storyboard failed | 剧本已交付，分镜停在第 N 镜 | 继续生成分镜 |
| ready + storyboard running | 剧本已交付，分镜生成中 | 查看分镜进度 |

空状态、徽标、按钮和错误提示全部从这个选择器生成，避免多处各自判断造成冲突。

### P2：降低长页面与轮询成本

- 手机端把能力边界、证据、统计和技术错误折叠到“详情”，首屏只留当前状态、主要操作和剧本摘要。
- 主线骨架、场次结构、辅助结构默认可折叠，并提供右侧/底部章节导航。
- picker 接口增加 `etag/updated_since` 或只返回 `id、episode_no、title、display_status`；运行状态用独立轻量接口或 SSE 推送。
- Evidence Drawer 增加 loading/error/retry，补焦点锁定和 Escape 关闭。
- 分集列表补 ArrowUp / ArrowDown / Enter 键盘操作和选中项自动滚动。

## 七、推荐整改顺序

1. **第一批（上线阻断）**：拆分“查看分镜/生成分镜”；运行态禁止直接保存；后端保存先 cancel-and-wait；接入 `expected_version`。
2. **第二批（核心体验）**：dirty guard、结构化场次编辑、台词时长预算、修复态约束生效、状态文案统一。
3. **第三批（效率与可访问性）**：移动端折叠、轮询减重、证据错误态、键盘导航、复制/导出/正文搜索。

## 九、最终建议

剧本台最值得保留的设计是：主线骨架、完整正文、场次结构和证据被放在同一工作台里，审阅链路完整；分集搜索在 1646 集规模下也能正常使用。

下一阶段不应继续增加字段或按钮，而应优先让每个按钮“只做它写出来的事情”，并确保所有运行态、保存态和版本态由同一套状态机约束。只要先解决隐藏副作用、保存竞态和编辑器结构化这三件事，剧本台会从“功能很多但不敢点”明显提升为“可放心用于生产”。
